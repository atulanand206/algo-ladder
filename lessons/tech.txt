### bigo
--idea
Big-O is a way to describe how the amount of work grows as the input gets bigger, ignoring the exact speed of the machine. Instead of "this takes 3 milliseconds", you say "this takes about n steps" or "about n squared steps", where `n` is the size of the input. Picture a queue at a shop: if each customer takes the same time, doubling the queue doubles the wait. If every customer must shake hands with every other customer, doubling the queue quadruples the handshakes.
The key insight is that only the fastest-growing part matters once `n` is large. `3n + 50` and `n` grow the same way, so both are written `O(n)`. This lets you judge an idea on paper, before you write any code, by asking "will the number of steps fit in the time limit?". A computer does roughly 100 million simple steps per second, which is the number to compare against.
--build
1. Decide what `n` is. It is the size of the input that makes the work grow (array length, number of nodes, number of queries). If there are several (`n` items and `q` queries), keep them as separate letters.
2. Count the steps of a single loop that runs `n` times doing constant work: that is `n`, written `O(n)`.
3. For nested loops, multiply: two loops of `n` each give `n * n`, written `O(n^2)`. Two loops one after the other add: `n + n` is still `O(n)`.
4. A loop that halves (or doubles) its counter each time runs `log2(n)` times, written `O(log n)`. A million items need only about 20 halvings.
5. A loop that does `O(log n)` work inside each of `n` iterations costs `O(n log n)`. Sorting is the common example.
6. Drop constants and smaller terms: `5n^2 + 100n + 7` becomes `O(n^2)`.
7. Compare your total to the budget: about `10^8` steps is fine, so `n = 10^5` allows `O(n log n)` or `O(n sqrt n)` but not `O(n^2)`.
--think
- Signal: you are about to write code and the limits say `n` is up to `10^5` or `10^6`. Work out the target complexity from `n` before choosing the idea. `n <= 20` hints at `2^n`, `n <= 500` allows `n^3`, `n <= 5000` allows `n^2`, `n <= 10^5` needs about `n log n`, and `n <= 10^9` needs `log n` or a formula.
- Count the worst case, not the average, unless the problem promises random input. Count the whole program: reading input, building structures and answering every query.
- If your idea is too slow, find which loop is the cost. Usually you can replace an inner loop by a lookup (prefix sums, hash map, binary search), which is the whole story of many techniques in this ladder.
- Space counts too: an array of `10^8` ints is 400 MB. Memory limits are usually 256 MB.
- Pitfalls: forgetting that a hash map or sort inside a loop costs something, treating `O(n)` string concatenation in a loop as free, counting `n` when the real size is the number of digits, and overflow when `n^2` no longer fits in a 32 bit int (use `long`).
--cost
Counting steps is itself free: it is a habit, not an algorithm. The examples below show linear, quadratic and logarithmic loops, and a slow versus fast way to find a pair with a given sum.
--java
// step counts for three growth rates
static long[] growth(int n) {
    long linear = 0, quadratic = 0, logarithmic = 0;
    for (int i = 0; i < n; i++) linear++;                 // n steps
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++) quadratic++;          // n * n steps
    for (int x = n; x > 1; x /= 2) logarithmic++;         // halving: log2(n) steps
    return new long[]{linear, quadratic, logarithmic};
}

// does the plan fit in about one second?

    return steps <= 100_000_000L;
}

// O(n^2): try every pair
static boolean hasPairSlow(int[] a, int target) {
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++)
            if (a[i] + a[j] == target) return true;
    return false;
}

// O(n): remember what we have seen, look up the partner
static boolean hasPairFast(int[] a, int target) {
    Set<Integer> seen = new HashSet<>();
    for (int x : a) {
        if (seen.contains(target - x)) return true;
        seen.add(x);
    }
    return false;
}

### amortized
--idea
Amortized analysis is a fair way to price an operation that is usually cheap but sometimes expensive. Think of a gym membership: you pay a small monthly fee even in months you never go, so that the occasional costly equipment is already paid for. Averaged over a long run of operations, the cost per operation is small, even if one single operation can be slow.
The insight is to count the total work over a whole sequence of operations, not the worst single one. A dynamic array that doubles its size when full copies many items on one push, but that doubling only happens after as many cheap pushes. Add it all up and the total copying is less than twice the number of pushes, so each push costs `O(1)` amortized.
--build
1. Name the operation sequence you care about: `n` operations in a row, starting from an empty structure.
2. Find the expensive event (a resize, a pop from a stack, a rebuild) and ask what must have happened before it could occur.
3. Method one, aggregate: count the total cost of all `n` operations, then divide by `n`. For doubling an array of size 1, 2, 4, ... the copies add up to `1 + 2 + 4 + ... < 2n`.
4. Method two, accounting: charge each cheap operation a few extra coins and store them as credit. The expensive event spends the credit, so it costs nothing new.
5. Method three, potential: pick a number (for example "items waiting on the stack") that rises on cheap steps and falls on expensive ones. The amortized cost is the real cost plus the change in that number.
6. Check that the credit or potential never goes negative, otherwise the argument is wrong.
--think
- Signal: a loop inside a loop where the inner loop looks like it could cost `O(n)` every time, but each item can only be removed or moved once. Stack tricks ("pop while smaller"), two pointers, and sliding windows all work this way.
- Ask: how many times can one item be touched in its whole life? If each item is pushed once and popped once, `n` items cost `2n` in total, no matter how the loops are nested.
- Amortized is not average case. It is a hard guarantee over any sequence of operations, with no randomness. It only fails for a single operation: one push may still be slow, which matters in real-time systems.
- Related: expected time (random) is about chance, amortized is about a sequence. Union-find with path compression and splay trees are both analysed with amortization.
- Pitfalls: claiming `O(1)` amortized when the structure can also shrink and then grow again repeatedly (halve the array at half full and you can thrash), and assuming every operation is cheap in a persistent or undo-able structure where you may repeat the expensive state.
--cost
Doubling dynamic array: `O(1)` amortized per push, `O(n)` total for `n` pushes. Monotone stack: `O(n)` total for `n` elements.
--java
// total element copies when n items are pushed one by one into an array that doubles
static long totalCopies(int n) {
    int capacity = 1, size = 0;
    long copies = 0;
    for (int i = 0; i < n; i++) {
        if (size == capacity) {      // full: copy everything into a bigger array
            copies += size;
            capacity *= 2;
        }
        size++;
    }
    return copies;                   // always below 2n
}

// next greater element for each index: -1 if none. Each index is pushed and popped once, so O(n)
static int[] nextGreater(int[] a) {
    int[] res = new int[a.length];
    Arrays.fill(res, -1);
    Deque<Integer> stack = new ArrayDeque<>();
    for (int i = 0; i < a.length; i++) {
        while (!stack.isEmpty() && a[stack.peek()] < a[i])
            res[stack.pop()] = i;    // the inner loop is paid for by earlier pushes
        stack.push(i);
    }
    return res;
}

vector<int> nextGreater(const vector<int>& a) {
    vector<int> res(a.size(), -1);
    vector<int> st;
    for (int i = 0; i < (int)a.size(); i++) {
        while (!st.empty() && a[st.back()] < a[i]) {

            st.pop_back();
        }
        st.push_back(i);
    }
    return res;
}
### recursion
--idea
Recursion solves a problem by solving a smaller copy of the same problem, then using that answer. Picture Russian nesting dolls: to open the whole set you open the outer doll, and what is inside is the same job on a smaller set. You keep going until you reach the smallest doll, which you can handle directly.
Every recursive function has two parts: a base case, the smallest input that you answer directly, and a recursive step, which reduces the input and trusts the function to solve the smaller version correctly. The trust is the insight: you do not trace every level in your head, you only check that the base case is right and that each step moves closer to it.
--build
1. Write down in one sentence what the function promises: "`hanoi(n, a, b, c)` moves `n` disks from peg `a` to peg `b` using `c`".
2. Pick the base case, the input so small the answer is obvious (`n == 0`: nothing to move). Return immediately there.
3. Write the recursive step by assuming the function already works for a smaller input. To move `n` disks: move `n - 1` disks out of the way, move the biggest disk, then move the `n - 1` disks back on top.
4. Check that every recursive call has a strictly smaller input, so the base case is always reached.
5. Combine the smaller answers into the answer for the full input.
6. Count the cost with a recurrence: Hanoi has `T(n) = 2 T(n-1) + 1`, so `T(n) = 2^n - 1` moves.
7. Second example, reversing an array: `reverseRange(a, i, j)` calls the piece `swap` to exchange the two ends, then trusts itself to reverse the inside `a[i+1..j-1]`. The base case is `i >= j`.
--think
- Signal: the problem contains a smaller copy of itself (trees, nested structures, "do this for the rest of the list", divide a range in half). If the statement defines something in terms of itself, recursion is the natural fit.
- Decide first the parameters that fully describe a subproblem. If the same subproblem appears many times, add a memo table; that is dynamic programming.
- Recursion with a loop that tries choices becomes backtracking. Splitting into halves and merging becomes divide and conquer. Turning the recursion into a loop with your own stack avoids stack overflow.
- Depth matters: most languages allow roughly 10^4 to 10^5 frames. A chain of `10^6` nodes needs an explicit stack or an iterative version.
- Pitfalls: missing base case (infinite recursion), a recursive call that does not shrink the input, doing the same work again and again without a memo, and sharing a mutable list between calls without copying.
--cost
Depends on the recurrence. Hanoi is `O(2^n)` time and `O(n)` stack depth. Each recursive solution costs (number of calls) times (work per call).

// moves for n disks from peg `from` to peg `to`, using `via` as spare
static void hanoi(int n, char from, char to, char via, List<String> moves) {

    hanoi(n - 1, from, via, to, moves);          // clear the way
    moves.add(from + "->" + to);                 // move the largest disk
    hanoi(n - 1, via, to, from, moves);          // put the rest back on top
}

### backtrack
--idea
Backtracking builds an answer one choice at a time. At each step you try an option, go deeper to see whether it can lead to a full answer, and if it fails (or after you have recorded the answer), you undo the choice and try the next option. Think of walking a maze and dropping a thread: when you hit a dead end you wind the thread back to the last fork and take a different branch.
The insight is the undo. Because every choice is reversed exactly before the next is tried, you can use one shared "current answer" (a list, a board) for the whole search instead of copying it each time. The search forms a tree of choices, and you walk it depth first.
--build
1. Decide what one choice is and what a complete answer looks like (for parentheses: add `(` or `)`, complete at length `2n`).
2. Keep shared state for the partial answer (`cur`) and any counters you need (`open`, `close`).
3. Write `solve(state)`. If the partial answer is complete, record a copy of it and return.
4. Otherwise loop over the legal choices. A choice is legal only if it can still lead to a valid answer: this check is where you cut dead branches.
5. For each legal choice: apply it (append to `cur`, update counters), call `solve` deeper, then undo it exactly.
6. Make sure the undo restores every piece of state you changed, so the next sibling choice starts from the same situation.
7. Second example, orderings by swapping: `permuteSwap` calls the piece `swap` to put each remaining item into position `start`, recurses, and calls `swap` again as the undo. No `used` array is needed because the array itself holds the choice.
--think
- Signal: "list all", "count all ways", "find any arrangement such that", with small limits (`n <= 20` or so) and no clean formula. Constraints like "no two adjacent equal" or "each used once" are the classic wording.
- Decide the order of choices (position by position, or item by item). A good order makes the legality check cheap and catches failure early.
- The power is in pruning: reject a partial answer as soon as it cannot be completed. Parentheses: never let `close` exceed `open`. Without the check you would explore all `2^(2n)` strings.
- If you only need a count or an optimum and subproblems repeat, switch to dynamic programming or memoization. If a constraint structure is rich (placing queens, Sudoku), look at the dedicated constraint search topics.
- Pitfalls: forgetting the undo, recording the live list instead of a copy, a legality test that is too weak (so you explore too much) or too strong (so you miss answers), and unbounded recursion depth.
--cost
Time is the number of nodes in the choice tree times the work per node. Without pruning it is exponential, for example `O(2^n)`. Generating balanced parentheses gives about `Catalan(n) * n` work. Space is `O(depth)`.
--java
static List<String> generateParens(int n) {
    List<String> out = new ArrayList<>();
    build(new StringBuilder(), 0, 0, n, out);
    return out;
}

static void build(StringBuilder cur, int open, int close, int n, List<String> out) {
    if (cur.length() == 2 * n) {                 // complete answer
        out.add(cur.toString());                 // record a copy
        return;
    }
    if (open < n) {                              // choice 1: add '('
        cur.append('(');
        build(cur, open + 1, close, n, out);
        cur.deleteCharAt(cur.length() - 1);      // undo
    }
    if (close < open) {                          // choice 2: add ')' only if one is open
        cur.append(')');
        build(cur, open, close + 1, n, out);
        cur.deleteCharAt(cur.length() - 1);      // undo
    }
}

// all orderings, built in place: swap each remaining item into position `start`, recurse, swap back
static void permuteSwap(int[] a, int start, List<List<Integer>> out) {
    if (start == a.length) {
        List<Integer> one = new ArrayList<>();
        for (int x : a) one.add(x);              // copy the finished ordering
        out.add(one);
        return;
    }
    for (int i = start; i < a.length; i++) {
        swap(a, start, i);                       // choose a[i] for this position
        permuteSwap(a, start + 1, out);
        swap(a, start, i);                       // undo
    }
}

def generate_parens(n):
    """All balanced strings of n pairs of parentheses."""
    out, cur = [], []

    def build(open_, close):
        if len(cur) == 2 * n:                    # complete answer
            out.append("".join(cur))             # record a copy
            return
        if open_ < n:                            # choice 1: add '('
            cur.append("(")
            build(open_ + 1, close)
            cur.pop()                            # undo
        if close < open_:                        # choice 2: add ')' only if one is open
            cur.append(")")
            build(open_, close + 1)
            cur.pop()                            # undo

    build(0, 0)
    return out

def permute_swap(a, start, out):
    """All orderings, built in place: swap each remaining item into position start, recurse, swap back."""
    if start == len(a):
        out.append(a[:])                         # copy the finished ordering
        return
    for i in range(start, len(a)):
        swap(a, start, i)                        # choose a[i] for this position
        permute_swap(a, start + 1, out)
        swap(a, start, i)                        # undo

### subsets
--idea
Generating subsets and permutations means listing every way to pick some of the items (subsets) or every way to order them (permutations). For three items `a, b, c` there are 8 subsets and 6 orderings. They are the two basic shapes of "try everything", and many harder problems are one of them with a filter on top.
Subsets: each item has two options, take it or skip it, so there are `2^n` subsets. Permutations: the first slot has `n` options, the next `n - 1`, and so on, so there are `n!` orderings. Both are done by backtracking, with a list for the current choice and an undo after each recursive call.
--build
1. For subsets by recursion, walk the items by index `i`. At each index make two recursive calls: one that skips `a[i]` and one that takes it (append, recurse, then remove).
2. When `i` reaches the end, the current list is one finished subset. Save a copy.
3. For subsets by counting, loop `mask` from `0` to `2^n - 1`. Each mask is a number whose binary digits say which items are in. The piece `itemsIn(mask, n)` returns the positions of the on bits, and you read `a[i]` for each one. No recursion and no undo.
4. For permutations, keep `used` as a bit mask (bit `i` on means item `i` is already placed). At each depth loop over all items; skip those where the piece `getBit(used, i)` is true.
5. Take item `i`: append it and recurse with `setBit(used, i)`. The mask is passed by value, so the recursive call changes only its own copy and there is nothing to undo for the mask. Remove the item from the list afterwards.
6. When the current list has `n` items, it is one finished ordering. Save a copy.
7. If the input has duplicates, sort it first and skip an item that equals the previous one when the previous one was not used in this position; otherwise you list the same answer many times.
--think
- Signal: "all subsets", "all orderings", "choose k of n", "every arrangement", with `n` up to about 20 for subsets and about 10 for permutations. If `n` is bigger, there must be structure to exploit.
- Decide whether order matters (permutation) or not (subset or combination). For combinations of size `k`, add a rule that the next index must be larger, so each set appears once.
- For subsets over small `n` with checks like "sum equals target", a bitmask loop from `0` to `2^n - 1` (see Enumerating subsets) is shorter than recursion. For half-size searching see meet in the middle.
- If you only need the count, a formula (`2^n`, `n!`, `n choose k`) or dynamic programming is far faster than listing.
- Pitfalls: saving the live list instead of a copy, duplicates in the input, and the sheer output size (`10!` is 3.6 million lists).
--cost
Subsets: `O(n * 2^n)` time (copying each answer). Permutations: `O(n * n!)`. Space is `O(n)` for the recursion plus the output.
--java
static List<List<Integer>> subsets(int[] a) {
    List<List<Integer>> out = new ArrayList<>();
    subsetsRec(a, 0, new ArrayList<>(), out);
    return out;
}

static void subsetsRec(int[] a, int i, List<Integer> cur, List<List<Integer>> out) {
    if (i == a.length) { out.add(new ArrayList<>(cur)); return; }   // copy the finished subset
    subsetsRec(a, i + 1, cur, out);                                 // skip a[i]
    cur.add(a[i]);
    subsetsRec(a, i + 1, cur, out);                                 // take a[i]
    cur.remove(cur.size() - 1);                                     // undo
}

// the same subsets, one per mask from 0 to 2^n - 1
static List<List<Integer>> subsetsByMask(int[] a) {
    int n = a.length;
    List<List<Integer>> out = new ArrayList<>();
    for (int mask = 0; mask < (1 << n); mask++) {
        List<Integer> one = new ArrayList<>();
        for (int i : itemsIn(mask, n)) one.add(a[i]);               // positions of the on bits
        out.add(one);
    }
    return out;
}

### nqueens
--idea
N-Queens asks you to place `n` queens on an `n` by `n` chessboard so that no two attack each other: no two share a row, a column or a diagonal. It is the standard example of constraint search: you place pieces one at a time and stop exploring a placement the moment it breaks a rule, instead of building a full board and checking afterwards.
The insight is that you place exactly one queen per row, so rows never clash. You only need to remember which columns and which two kinds of diagonal are already taken. Keeping those as bits in a few integers makes "which squares are free in this row" a single operation.
--build
1. Process rows from `0` to `n - 1`. In each row choose one column for the queen.
2. Keep three bit masks: `cols` (taken columns), `d1` (taken diagonals going down-left) and `d2` (taken diagonals going down-right). A set bit means "attacked".
3. In row `r`, the free squares are `free = ~(cols | d1 | d2) & ((1 << n) - 1)`. The final mask trims the bits beyond column `n - 1`.
4. Pull one free square at a time with `bit = free & -free` (the lowest set bit), then `free -= bit`.
5. Place the queen: recurse into row `r + 1` with `cols | bit`, `(d1 | bit) << 1` and `(d2 | bit) >> 1`. The shifts slide the diagonals one column sideways as the row advances.
6. When `r == n`, all queens are placed: that is one solution. Add one to the count.
7. To check a finished placement independently, `isValidPlacement` lays the queens on a flat board with the piece `idx(r, c, n)` and walks along each line with `inBounds` so it never steps off the board. Use it to test any solver you write.
--think
- Signal: place objects on a grid or in slots under "no two may conflict" rules, with `n` up to about 15. Also Sudoku, graph colouring and scheduling with conflicts.
- Choose the order of decisions so that the most constrained thing goes first, and test conflicts in constant time (bit masks, boolean arrays) rather than rescanning the board.
- Prune early: the whole speed comes from rejecting a bad partial placement at once. For `n = 8` the search visits about 2000 nodes, not `8^8` = 16 million.
- Symmetry: the board can be mirrored, so you can place only half of the first row and double the result (careful when `n` is odd). Useful when `n` is near the limit.
- If the problem is "exact cover" (every row, column and constraint used exactly once), dancing links is the sharper tool. If constraints form a graph, consider matching or flow.
- Pitfalls: wrong direction on the diagonal shifts, forgetting to mask the high bits, and trying to reuse the masks after recursion (they are passed by value, so no undo is needed).
--cost
Time is exponential, but with pruning it is small: `n = 12` has 14200 solutions and takes a fraction of a second, `n = 15` is about 2.3 million solutions. Space `O(n)` for the recursion.

// count placements for rows row..n-1 given the attacked columns and diagonals
static int place(int n, int row, int cols, int d1, int d2) {
    if (row == n) return 1;                                  // every row has a queen
    int count = 0;
    int free = ~(cols | d1 | d2) & ((1 << n) - 1);           // safe squares in this row
    while (free != 0) {
        int bit = free & -free;                              // take the lowest safe square
        free -= bit;
        // diagonals shift one column per row
        count += place(n, row + 1, cols | bit, (d1 | bit) << 1, (d2 | bit) >> 1);
    }
    return count;
}


// check a finished placement: cols[r] is the column of the queen in row r
static boolean isValidPlacement(int n, int[] cols) {
    boolean[] queen = new boolean[n * n];
    for (int r = 0; r < n; r++) queen[idx(r, cols[r], n)] = true;
    int[][] steps = {{0, 1}, {1, 0}, {1, 1}, {1, -1}};   // row, column, and both diagonals (one way each)
    for (int r = 0; r < n; r++)
        for (int[] s : steps) {
            int rr = r + s[0], cc = cols[r] + s[1];
            while (inBounds(rr, cc, n, n)) {              // walk away from the queen along the line
                if (queen[idx(rr, cc, n)]) return false;  // another queen on the same line attacks it
                rr += s[0]; cc += s[1];
            }
        }
    return true;
}

### dlx
--idea
Dancing links (DLX) solves the exact cover problem: given a grid of 0s and 1s, pick some rows so that every column has exactly one 1 among the picked rows. Many puzzles are exact cover in disguise: Sudoku, pentomino tilings, N-Queens, scheduling. Each row is a possible move, each column is a rule that must be met exactly once.
The trick is a data structure in which every 1 is a node in two circular doubly linked lists, one across its row and one down its column. To remove a node from a list you do `L[R[x]] = L[x]; R[L[x]] = R[x]`, but the node itself keeps its own pointers. So putting it back is the exact reverse and costs nothing: the links "dance". This gives backtracking an instant undo.
--build
1. Make a header node for each column, in a circular list with a root node `0` (so columns are `1..n`). Each header has `S[c]`, the number of 1s still in the column.
2. Add one node per 1 in the grid. Link it at the bottom of its column list (`U`, `D` pointers), set its column header `C[x]`, remember its row number `RW[x]`, and link the nodes of one row into a circle (`L`, `R`).
3. `cover(c)`: unlink header `c` from the header list. Then for every row `i` going down column `c`, for every other node `j` in row `i`, unlink `j` from its column (`U[D[j]] = U[j]; D[U[j]] = D[j]`) and decrease `S[C[j]]`. This deletes every row that uses column `c`, because choosing one of them would break "exactly once".
4. `uncover(c)`: do the same loops in the opposite order (up the column, left along the row) and reverse every operation. Order matters: it must mirror `cover` exactly.
5. `search`: if the header list is empty (`R[0] == 0`), all columns are satisfied: success. Otherwise pick the column `c` with the smallest `S[c]` (fewest options, fails fastest).
6. Cover `c`. For each row `r` in column `c`: add `RW[r]` to the solution, cover the column of every other node in row `r`, recurse. If the recursion fails, uncover those columns in reverse order and remove `RW[r]`.
7. After trying all rows, uncover `c` and return failure. In the code below, `exactCover` returns the first solution found.
--think
- Signal: "place pieces so that every cell/rule is covered exactly once": Sudoku, tilings, "choose a set of items so every element is in exactly one chosen item". If a naive backtracking tries many dead ends, DLX is the fast version.
- The modelling step is the real thinking. Write down every possible move as a row, and every rule as a column. Sudoku has 4 kinds of rule (each cell filled, each row has digit d, each column has d, each box has d), so 324 columns and 729 rows.
- Choosing the column with the fewest rows is the heuristic that makes it fast: a column with `S = 0` means dead end right now, `S = 1` means a forced move.
- Pitfall: uncovering in the wrong order corrupts the lists silently. Always uncover in the reverse order of covering.
- Optional columns (like diagonals in N-Queens, which may be used at most once) can be kept out of the header ring so they never have to be covered.
- Neighbours: plain backtracking with bit masks (N-Queens) is simpler if there are only a couple of constraints. For counting rather than listing, dynamic programming over masks can be better.
--cost
Exponential in the worst case, but pruned very hard in practice: a Sudoku solves in microseconds to milliseconds. Memory is `O(number of ones)`.

static int[] L, R, U, D, C, S, RW;
static List<Integer> sol;

static void cover(int c) {
    L[R[c]] = L[c]; R[L[c]] = R[c];                       // unlink the column header
    for (int i = D[c]; i != c; i = D[i])
        for (int j = R[i]; j != i; j = R[j]) {            // unlink the rest of every row using c
            U[D[j]] = U[j]; D[U[j]] = D[j]; S[C[j]]--;
        }
}

static void uncover(int c) {
    for (int i = U[c]; i != c; i = U[i])                  // exact reverse of cover
        for (int j = L[i]; j != i; j = L[j]) {
            S[C[j]]++; U[D[j]] = j; D[U[j]] = j;
        }
    L[R[c]] = c; R[L[c]] = c;
}

static boolean search() {
    if (R[0] == 0) return true;                           // all columns covered
    int c = R[0];
    for (int j = R[c]; j != 0; j = R[j]) if (S[j] < S[c]) c = j;   // fewest options first
    cover(c);
    for (int r = D[c]; r != c; r = D[r]) {
        sol.add(RW[r]);
        for (int j = R[r]; j != r; j = R[j]) cover(C[j]);
        if (search()) return true;
        for (int j = L[r]; j != r; j = L[j]) uncover(C[j]);
        sol.remove(sol.size() - 1);
    }
    uncover(c);
    return false;
}

### brute
--idea
Brute force means trying every possibility and picking the one that works. It is the honest first answer to any problem: if you can list all candidates and test each one, you have a correct solution, even if it is slow. Pruning is the upgrade: while you build a candidate, notice early that it cannot possibly succeed, and stop wasting time on everything that would follow.
Think of looking for your keys. Brute force checks every pocket and every room. Pruning says "I was never in the garage, skip it". The answer stays exactly the same, only the useless work disappears. And a brute force solution is also the best tool for testing a clever one: run both on small inputs and compare.
--build
1. State the search space: what is one candidate, and how many are there? (Subsets of `n` items: `2^n`.)
2. Check the limits. If the count fits the budget (`10^7` or `10^8` simple steps), plain brute force is the answer. Stop here.
3. Write the search as a recursion that decides items one at a time (`rec(i, remaining)`).
4. Add a stopping test at the top: success (`remaining == 0`), or failure (`remaining < 0`).
5. Add a bound: a cheap calculation that says "even in the best case from here I cannot reach the goal". In the code, `suffix[i]` is the total of everything still available, so if it is below `remaining`, we stop.
6. Order the decisions so that failures show up early (largest items first often helps).
7. Keep a plain, slow version around and compare answers on random small inputs.
8. The plain version `canSumPlain` tries every mask from `0` to `2^n - 1` and reads each bit with the piece `getBit`. Keep it as the slow reference and compare the pruned `canSum` against it on random small inputs (step 7).
--think
- Signal: very small limits (`n <= 20`, a board of `4 x 4`), "does there exist", or no pattern visible yet. Also the first thing to write when you are stuck: a brute force often reveals the pattern that leads to the real solution.
- Always do the arithmetic: candidates times cost per check. If it is under about `10^8`, submit the brute force.
- Pruning ideas: a bound on what is still reachable, stopping at the first success when only existence matters, skipping duplicates, and symmetry. Each cut must be provably safe (never removes a valid answer).
- If many branches lead to the same state, memoize it (dynamic programming). If a clear local rule picks the best choice, a greedy method is much faster.
- As a testing tool: write brute force first, a fast solution second, then loop over random tiny cases and compare. This finds most bugs.
- Pitfalls: pruning with a bound that is not valid for negative numbers (the example assumes values are non-negative), exploring in an order where nothing is pruned, and forgetting to check the empty or minimal cases.
--cost
Worst case is the full search space, `O(2^n)` here. With good pruning it is usually far smaller, but the worst case does not improve.

// can some subset of the non-negative numbers sum to exactly target?
static boolean canSum(int[] a, int target) {
    int n = a.length;
    long[] suffix = new long[n + 1];                      // suffix[i] = a[i] + ... + a[n-1]
    for (int i = n - 1; i >= 0; i--) suffix[i] = suffix[i + 1] + a[i];
    return rec(a, suffix, 0, target);
}

static boolean rec(int[] a, long[] suffix, int i, long remaining) {
    if (remaining == 0) return true;                      // success
    if (remaining < 0 || i == a.length || suffix[i] < remaining) return false;   // prune
    return rec(a, suffix, i + 1, remaining - a[i])        // take a[i]
        || rec(a, suffix, i + 1, remaining);              // skip a[i]
}


// the plain version, no pruning: try every mask of chosen items (n <= 30)
static boolean canSumPlain(int[] a, int target) {
    for (int mask = 0; mask < (1 << a.length); mask++) {
        long sum = 0;
        for (int i = 0; i < a.length; i++)
            if (getBit(mask, i)) sum += a[i];                 // item i is chosen in this mask
        if (sum == target) return true;
    }
    return false;
}

def can_sum(a, target):
    """Can some subset of the non-negative numbers sum to exactly target?"""
    n = len(a)
    suffix = [0] * (n + 1)                       # suffix[i] = a[i] + ... + a[n-1]
    for i in range(n - 1, -1, -1):
        suffix[i] = suffix[i + 1] + a[i]

    def rec(i, remaining):
        if remaining == 0:                       # success
            return True
        if remaining < 0 or i == n or suffix[i] < remaining:   # prune
            return False
        return rec(i + 1, remaining - a[i]) or rec(i + 1, remaining)   # take, or skip

    return rec(0, target)


def can_sum_plain(a, target):
    """The plain version, no pruning: try every mask of chosen items."""
    for mask in range(1 << len(a)):
        total = sum(a[i] for i in range(len(a)) if get_bit(mask, i))   # item i is chosen in this mask
        if total == target:
            return True
    return False
--cpp
bool rec(const vector<int>& a, const vector<long long>& suffix, int i, long long remaining) {
    if (remaining == 0) return true;                      // success
    if (remaining < 0 || i == (int)a.size() || suffix[i] < remaining) return false;   // prune
    return rec(a, suffix, i + 1, remaining - a[i])        // take a[i]
        || rec(a, suffix, i + 1, remaining);              // skip a[i]
}

// can some subset of the non-negative numbers sum to exactly target?
bool canSum(const vector<int>& a, int target) {

    for (int i = n - 1; i >= 0; i--) suffix[i] = suffix[i + 1] + a[i];
    return rec(a, suffix, 0, target);
}

### prefix
--idea
A prefix sum array stores, for every position, the total of all items up to that position. Once you have it, the sum of any range of the array is one subtraction: the total up to the end of the range minus the total up to just before its start. It is like a running odometer on a car: the distance of any trip is the reading at the end minus the reading at the start.
The insight is to pay `O(n)` once to build the table so that every later range question costs `O(1)` instead of `O(n)`. The same trick answers harder questions: if two prefix totals are equal, everything between them adds up to zero, and if two totals differ by `k`, the part between them adds up to `k`.
--build
1. Make an array `p` of size `n + 1` with `p[0] = 0`. The extra slot at the front is the "empty prefix" and removes edge cases.
2. Fill it: `p[i + 1] = p[i] + a[i]`. So `p[i]` is the sum of the first `i` items.
3. Answer "sum of `a[l..r]` (both ends included)" as `p[r + 1] - p[l]`.
4. For "how many subarrays sum to `k`": walk once keeping the running total `sum`. A subarray ending here sums to `k` exactly when some earlier prefix equals `sum - k`. Keep a map from prefix value to how many times it has occurred, started with `{0: 1}` for the empty prefix.
5. At each item: add `seen[sum - k]` to the answer, then record `sum` in the map. Record after counting, so an empty subarray is never counted.
6. In code, steps 1 and 2 are the piece `buildPrefix` and step 3 is the piece `rangeSum`. `bestWindowSum` calls both to find the best run of `k` items: one subtraction per window instead of adding `k` numbers. Step 4 to 5 is `countSubarraysWithSum`, which is new here.
--think
- Signal: many queries of the form "sum (or count) over a range" on data that does not change. Also "subarray with sum exactly `k`", "equal number of 0s and 1s" (turn 0 into -1), "sum divisible by `m`" (prefix values mod `m`).
- Decide first what quantity is additive. Anything you can add and subtract works: sums, counts of a letter, XOR (it undoes itself), but not min or max.
- If values change between queries, a prefix array breaks: use a Fenwick tree or segment tree. If you need to apply many range updates and read once, use a difference array, which is the inverse of prefix sums.
- For subarray counts with positive values only, two pointers works too. With negative numbers it does not (shrinking the window may not reduce the sum), so use prefix sums with a hash map.
- Pitfalls: off-by-one between `p[r]` and `p[r + 1]`, overflow (`n * value` can exceed 32 bits, use `long`), and forgetting the `{0: 1}` start so subarrays starting at index 0 are missed.
--cost
Build `O(n)` time and space, each range query `O(1)`. Counting subarrays with a given sum is `O(n)` expected with a hash map.
--java
// largest sum of k consecutive items (k <= a.length)
static long bestWindowSum(int[] a, int k) {
    long[] p = buildPrefix(a);                          // piece: p[i] = sum of the first i items
    long best = Long.MIN_VALUE;
    for (int l = 0; l + k <= a.length; l++)
        best = Math.max(best, rangeSum(p, l, l + k - 1));   // piece: one subtraction per window
    return best;
}

### diffarr
--idea
A difference array lets you add a number to a whole range of an array in constant time, no matter how long the range is. You do not touch the range at all. Instead you mark where the extra amount starts and where it stops, and later one pass of running totals spreads it into place. Think of a road with traffic lights: you note "from here the speed limit goes up by 10" and "from here it goes back down", and only compute actual speeds when you drive.
It is the exact reverse of a prefix sum. If `d[i] = a[i] - a[i - 1]` (the change between neighbours), then running totals of `d` give back `a`. Adding `v` to `a[l..r]` changes the differences at only two places: `d[l]` goes up by `v` and `d[r + 1]` goes down by `v`.
--build
1. Make `d` with `n + 1` zeros (one extra slot so `r + 1` is always valid).
2. For every update "add `v` to positions `l..r`": do `d[l] += v` and `d[r + 1] -= v`.
3. After all updates, make one pass: `cur = 0; for i in 0..n-1: cur += d[i]; a[i] = cur`.
4. If the array already had values, add them in at the end (or start `d` from the original differences).
5. You can only read the array after the final pass. If you must read between updates, use a Fenwick tree instead.
6. In code, step 2 is the piece `rangeAdd(d, l, r, v)` and step 3 is the piece `materialize(d)`. `applyRangeAdds` is just those two calls plus the spare slot, trimmed back to length `n` at the end.
--think
- Signal: many updates of the form "add `v` to every element from `l` to `r`", then a question about the final array. Typical wording: "`m` operations, each increases a segment", flight bookings, booking calendars, painting segments, counting how many intervals cover each point.
- Decide whether updates all come first and reads come after (difference array, `O(n + m)`) or are mixed (Fenwick or lazy segment tree, `O(log n)` each).
- It extends to two dimensions (add to a rectangle with four corner marks) and works for "count how many intervals cover each point": add 1 at each start, subtract 1 after each end.
- Counting coverage on huge coordinates: combine with coordinate compression or a sweep line over sorted events.
- Pitfalls: forgetting the `r + 1` slot (out of range when `r = n - 1`), off-by-one if ranges are half-open, and mixing 0-based and 1-based indices.
--cost
`O(1)` per update, `O(n)` for the final pass. Space `O(n)`.
--java
// ops[i] = {l, r, v}: add v to positions l..r (inclusive). Returns the final array.
static long[] applyRangeAdds(int n, int[][] ops) {
    long[] d = new long[n + 1];                      // one spare slot for r + 1
    for (int[] op : ops)
        rangeAdd(d, op[0], op[1], op[2]);            // piece: mark the start and the stop
    long[] a = materialize(d);                       // piece: running total spreads the marks out
    return Arrays.copyOf(a, n);                      // drop the spare slot
}

### prefix2d
--idea
A 2D prefix sum table lets you add up any rectangle of a grid with just four lookups. Imagine each cell of the table holding the total of the rectangle that starts at the top left corner of the grid and ends at that cell. To get some other rectangle, take the big rectangle that ends at its bottom right corner and cut off the strips above and to the left.
The cutting uses inclusion and exclusion: subtracting the strip above and the strip to the left removes the top left overlap twice, so you add that corner back once. Building the table uses the same idea in one sweep.
--build
1. Make `P` with `h + 1` rows and `w + 1` columns, all zeros. Row 0 and column 0 are empty padding so that no case needs special handling.
2. Fill in reading order: `P[i + 1][j + 1] = grid[i][j] + P[i][j + 1] + P[i + 1][j] - P[i][j]`. Add the cell, add the block above and the block to the left, subtract the corner counted twice.
3. To sum the rectangle with top left `(r1, c1)` and bottom right `(r2, c2)`, both included: `P[r2 + 1][c2 + 1] - P[r1][c2 + 1] - P[r2 + 1][c1] + P[r1][c1]`.
4. Say the four terms out loud: whole, minus top strip, minus left strip, plus the corner removed twice.
5. In code, steps 1 and 2 are the piece `build2d`. Steps 3 and 4 are `rectSum`, which is new here. `bestBlock` calls both to find the best fixed-size block in `O(hw)` total.
--think
- Signal: many queries asking for the sum or count inside rectangles of a static grid: number of 1s in a submatrix, total in a window, "largest square with sum at most `S`".
- The grid must not change. If cells are updated, use a 2D Fenwick tree. If updates are rectangle additions, use a 2D difference array.
- It works for anything with an inverse: sums, counts, XOR. Not for max or min.
- To count something like "cells equal to 5", first make an indicator grid (1 where true), then take the prefix table. Do one table per letter or value if the alphabet is tiny.
- Combine with binary search for "biggest square whose sum fits" or with a fixed window size to find the best window in `O(hw)`.
- Pitfalls: mixing the padded and unpadded coordinates (the off-by-one is the whole difficulty), integer overflow on large grids, and forgetting to add the corner back.
--cost
Build `O(hw)` time and space, each query `O(1)`.
--java
// sum of the rectangle with corners (r1,c1) and (r2,c2), both included; p comes from build2d
static long rectSum(long[][] p, int r1, int c1, int r2, int c2) {
    return p[r2 + 1][c2 + 1] - p[r1][c2 + 1] - p[r2 + 1][c1] + p[r1][c1];
}

        for (int c = 0; c + bw <= g[0].length; c++)
            best = Math.max(best, rectSum(p, r, c, r + bh - 1, c + bw - 1));
    return best;
}

### twop
--idea
Two pointers means walking two markers through an array, usually from opposite ends or one behind the other, so that together they cover the data once instead of checking every pair. Picture two people searching a sorted bookshelf from both ends: if the sum of the two books they hold is too big, the right person steps left; if too small, the left person steps right.
The insight is that each step throws away a whole group of candidates that can no longer be the answer. With a sorted array, if `a[lo] + a[hi]` is too big, then `a[hi]` is too big with every partner from `lo` onwards, so `hi` can be dropped for good. Every step permanently discards at least one item, so the walk takes `n` steps in total instead of `n^2` pairs.
--build
1. Sort the array first if order does not matter to the problem (sorting costs `O(n log n)`).
2. Place `lo = 0` and `hi = n - 1` (opposite ends), or both at the start (same direction, "fast and slow").
3. Compute the quantity for the current pair: `s = a[lo] + a[hi]`.
4. If `s` is too small, you need a bigger value: `lo++`. If `s` is too big: `hi--`. If it matches, record it.
5. Repeat while `lo < hi`. Each iteration moves at least one pointer, so it ends.
6. For counting pairs with sum at most `t`: when `s <= t`, every index from `lo + 1` to `hi` also works as a partner for `lo`, so add `hi - lo` and move `lo`.
7. Same-direction version (`moveZeroes`): `read` scans every item and `write` marks where the next non-zero item belongs. Each time `read` finds a non-zero item, step 4's move is the piece `swap(a, write, read)`, then `write` advances. The zeroes drift to the end.
--think
- Signal: a sorted array (or one you may sort) and a question about pairs or ranges: "two numbers that sum to", "closest pair", "remove duplicates in place", "merge two sorted lists", "container with most water", "palindrome check".
- Decide what moving each pointer means. The proof is: "if I move this pointer, I only discard options that can never be the answer", the same style of argument as binary search.
- Opposite ends suits sorted pair problems. Same direction (one reads, one writes, or a window with two ends) suits in-place filtering and subarray conditions; see sliding window.
- If the array is not sorted and the order matters, two pointers on opposite ends fails; use a hash map. If you need three numbers, fix one and run two pointers on the rest: `O(n^2)`.
- Pitfalls: moving the wrong pointer, infinite loops when no pointer moves, not handling duplicates when you must list distinct pairs, and using it on negative numbers for subarray sums (use prefix sums instead).
--cost
Time `O(n)` after sorting (`O(n log n)` including the sort). Space `O(1)`.
--java
// sorted a: indices {i, j} with a[i] + a[j] == target, or {-1, -1}
static int[] pairWithSum(int[] a, int target) {
    int lo = 0, hi = a.length - 1;
    while (lo < hi) {
        int s = a[lo] + a[hi];
        if (s == target) return new int[]{lo, hi};
        if (s < target) lo++;       // need something bigger
        else hi--;                  // need something smaller
    }
    return new int[]{-1, -1};
}

// sorted a: how many pairs i < j have a[i] + a[j] <= target
static long countPairsAtMost(int[] a, int target) {

    long count = 0;
    while (lo < hi) {
        if (a[lo] + a[hi] <= target) {
            count += hi - lo;       // a[lo] works with every index lo+1..hi
            lo++;
        } else hi--;                // a[hi] is too big for a[lo], so for every later lo too
    }
    return count;
}

### window
--idea
A sliding window is a range `[left, right]` over an array or string that you stretch on the right and shrink on the left, while keeping a running summary of what is inside (a sum, a set of letters, a count). Think of a caterpillar crawling along: the head moves forward to take in a new item, and the tail moves up whenever the body gets too long or breaks a rule.
The insight is that both ends only ever move forward, so each item enters the window once and leaves once. You never recompute the summary from scratch: you add the entering item and remove the leaving one, so the total work is `O(n)` instead of `O(n^2)` for trying every range.
--build
1. Decide what the window must satisfy (no repeated letters, sum at least `target`, at most `k` distinct values) and what summary you keep (a map of last positions, a running sum, a count table).
2. Start `left = 0`. Loop `right` from `0` to `n - 1`: add `a[right]` to the summary.
3. While the window breaks the rule (or, for "shortest window", while it still satisfies the rule), remove `a[left]` from the summary and move `left` forward.
4. After the shrink step the window is valid (or minimal). Update the best answer with its length `right - left + 1`.
5. For "longest window with no repeated letter", keep `last[c]`, the most recent index of letter `c`. When `s[right]` was seen at an index at or after `left`, jump `left` to one past it.
6. For "shortest subarray with sum at least `target`" (positive numbers only), keep `sum`, and shrink while `sum >= target`, recording lengths.
7. The piece `longestWindow(a, k)` is step 2 and 3 for the rule "at most `k` distinct values": it adds `a[right]` to a count table and shrinks from the left while there are more than `k` kinds. `longestTwoKinds` calls it with `k = 2`. The other two examples above change the rule and the summary, but keep the same loop shape.
--think
- Signal: "longest or shortest contiguous subarray or substring such that ...", "at most `k` distinct", "no repeats", "sum at least `S`", or windows of a fixed size `k`.
- The crucial check is monotonicity: if a window is valid, shrinking it keeps it valid (or growing keeps it broken). Then the left pointer never has to go backwards. This holds for positive numbers, counts, distinct counts. It fails with negative numbers: use prefix sums with a hash map instead.
- Longest window: grow always, shrink only when invalid. Shortest window: grow until valid, then shrink as much as possible. Counting windows: for each `right`, the number of valid `left` values is often `right - left + 1`.
- "Exactly `k`" can be done as "at most `k`" minus "at most `k - 1`".
- For the maximum or minimum inside a window, a plain summary is not enough; use a deque (sliding window maximum).
- Pitfalls: shrinking too little (window still invalid), moving `left` backwards when using `last[c]` (take the max), off-by-one in the length, and mixing up "longest" and "shortest" loop shapes.
--cost
Time `O(n)` (each pointer moves at most `n` times). Space `O(alphabet)` or `O(window)`.
--java
// length of the longest substring with no repeated letter
static int longestUnique(String s) {
    Map<Character, Integer> last = new HashMap<>();   // letter -> most recent index
    int left = 0, best = 0;
    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        if (last.containsKey(c) && last.get(c) >= left)
            left = last.get(c) + 1;                   // jump past the earlier copy
        last.put(c, right);
        best = Math.max(best, right - left + 1);
    }
    return best;
}

// shortest subarray (positive numbers) with sum >= target, 0 if none
static int shortestAtLeast(int[] a, long target) {
    int left = 0, best = 0;
    long sum = 0;

### windeque
--idea
The sliding window maximum problem asks for the biggest value inside every window of `k` consecutive items as the window slides along an array. Rescanning each window costs `O(nk)`. A deque (a queue you can push to and pop from at both ends) does it in `O(n)` by remembering only the items that could still become a maximum.
The insight: if a new item is bigger than some item sitting earlier in the window, that older item can never be the maximum again. It is smaller and it will also leave the window sooner. So throw it away. What remains in the deque, front to back, is a decreasing list of candidates, and the front is always the current maximum.
--build
1. Keep a deque `dq` of indices (not values), so you can tell when an index has left the window.
2. For each new index `i`: while the deque is not empty and `a[dq.back] <= a[i]`, pop from the back. Those items are dominated by the new one.
3. Push `i` on the back.
4. If the front index is `<= i - k`, it has slid out of the window: pop from the front.
5. Once `i >= k - 1` the first window is complete, so the answer for this window is `a[dq.front]`. Record it.
6. For a minimum, flip the comparison in step 2.
--think
- Signal: "maximum or minimum of every window of size `k`", or any range max/min where both ends only move forward. Also dynamic programming transitions like `dp[i] = best over dp[i - k..i - 1] + cost`, which is exactly a sliding window maximum.
- The invariant: indices in the deque are increasing and their values are decreasing. The back is always the newest item, the front always the best.
- Use a segment tree or sparse table when windows are arbitrary (not sliding in one direction). Use two heaps or a sorted structure for the median.
- Decide `<=` or `<` when popping: with `<=` equal items are dropped in favour of the newest, which is correct and keeps the deque short.
- Pitfalls: storing values instead of indices (cannot expire them), checking the expiry before adding the new item, and an off-by-one in the window start (`i - k + 1`).
--cost
Time `O(n)`: every index is pushed once and popped at most once. Space `O(k)`.
--java
static int[] slidingMax(int[] a, int k) {
    int n = a.length;
    int[] res = new int[n - k + 1];
    Deque<Integer> dq = new ArrayDeque<>();           // indices, values decreasing
    for (int i = 0; i < n; i++) {
        while (!dq.isEmpty() && a[dq.peekLast()] <= a[i])
            dq.pollLast();                            // dominated by the new item
        dq.addLast(i);
        if (dq.peekFirst() <= i - k) dq.pollFirst();  // slid out of the window
        if (i >= k - 1) res[i - k + 1] = a[dq.peekFirst()];
    }
    return res;
}
--py
from collections import deque

def sliding_max(a, k):
    """Maximum of every window of k consecutive items."""
    res, dq = [], deque()                             # dq holds indices, values decreasing
    for i, x in enumerate(a):
        while dq and a[dq[-1]] <= x:
            dq.pop()                                  # dominated by the new item
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()                              # slid out of the window
        if i >= k - 1:
            res.append(a[dq[0]])
    return res

### fastslow
--idea
Fast and slow pointers walk the same path at two speeds: the slow one takes one step at a time, the fast one takes two. On a path that ends, the fast pointer reaches the end when the slow one is exactly halfway, which finds the middle in one pass. On a path that loops back on itself, the fast one laps the slow one and they meet inside the loop, which proves a cycle exists. It is two runners on a track: if the track is a loop, the faster runner must catch the slower one.
To find where the loop starts, use a second observation. When they meet, move one pointer back to the head and then walk both one step at a time. They will meet again exactly at the first node of the cycle. The distances work out so that the head and the meeting point are the same number of steps away from the cycle start.
--build
1. Nodes are `ListNode` objects with a value `val` and a pointer `next` (null at the end of the list). Start at `head`.
2. Set `slow = fast = head`.
3. Loop while `fast` and `fast.next` are not null: move `slow` one step, `fast` two steps.
4. If `slow == fast` after a move, there is a cycle. If the loop ends because `fast` ran off the end, there is none.
5. To find the cycle start: put `slow = head`, keep `fast` at the meeting point, and step both by one until they are equal. That node is the first node of the cycle.
6. To find the middle of a list with no cycle, use the same loop without the meeting check: when it stops, `slow` is the middle (the second of the two middles when the length is even).
7. To test whether a list is a palindrome: find the middle, call the piece `reverseList` on the half that starts at the middle, then walk the first half and the reversed half together comparing `val`.
--think
- Signal: a linked list or any "next" function (`x -> f(x)`) where you need to detect a cycle, find where it starts, find its length, or find the middle without knowing the length. Also "happy number", "find the duplicate in an array of `n + 1` numbers in `1..n`" (treat `a[i]` as a next pointer), and repeating sequences in simulations.
- The proof for the cycle start: let the head be `a` steps from the cycle start and the meeting point be `b` steps past the start. The fast pointer has travelled twice as far as the slow one, so `a + b` is a multiple of the cycle length. Therefore walking `a` more steps from the meeting point returns to the cycle start, exactly where the pointer from the head arrives.
- The cycle length: after meeting, walk one pointer around until it returns to the meeting point and count the steps.
- Alternatives: a hash set of visited nodes is simpler but uses `O(n)` memory. Brent's algorithm is a faster variant of the same two-speed idea.
- Pitfalls: checking `next[fast]` before checking `fast` (null access), starting the loop condition wrong so an empty list crashes, and assuming the meeting point is the cycle start (it is not).
--cost
Time `O(n)`, space `O(1)`.
--java
// ListNode has an int val and a ListNode next (null at the end)

// first node of the cycle, or null if the list ends
static ListNode cycleStart(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;                   // one step
        fast = fast.next.next;              // two steps
        if (slow == fast) {                 // they met inside the cycle
            slow = head;
            while (slow != fast) {          // equal distances now: walk together
                slow = slow.next;
                fast = fast.next;
            }
            return slow;
        }
    }
    return null;
}

// middle node of a list with no cycle (the second middle when the length is even)
static ListNode middle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow;
}

// palindrome test for a list with no cycle; it reverses the second half in place
static boolean isPalindrome(ListNode head) {
    ListNode back = reverseList(middle(head));      // piece: flip the second half
    for (ListNode front = head; back != null; front = front.next, back = back.next)
        if (front.val != back.val) return false;
    return true;
}

### greedy
--idea
A greedy algorithm builds an answer step by step and, at every step, takes the choice that looks best right now, never reconsidering it later. Think of making change at a till: to pay out 63 in coins of 25, 10, 5 and 1, you hand over the biggest coin that still fits, again and again, and you end with the fewest coins. No planning ahead, no undoing.
Greedy is only correct when a local best choice can always be extended to a global best answer. That is a property you must prove, not assume. For coins 25, 10, 5, 1 it holds. For coins 4, 3, 1 and the amount 6, greedy picks 4, 1, 1 (three coins) but 3, 3 (two coins) is better. So the real skill is knowing when it is safe.
--build
1. Define what a "step" is and what "best right now" means. Write it as a rule that needs no lookahead (biggest coin that fits, interval that ends earliest, item with best ratio).
2. Often the rule needs the data in a certain order: sort by the criterion, or keep a heap of candidates so the best one is always at hand.
3. Run the loop: look at the best candidate, check it is allowed (still fits, does not conflict), take it, update the remaining problem.
4. Stop when nothing more can be taken or the goal is met.
5. Prove it (before trusting it): show that there is an optimal solution that contains your first choice (exchange argument), then that the rest is the same problem but smaller.
6. Test against a brute force on small inputs; a greedy that is wrong usually fails on a tiny case.
7. Worked example in code: `minJumps` is greedy. At each index it tracks the `farthest` place reachable with one more jump, using the piece `clamp` to cap it at the last index, and jumps only when it must (at `curEnd`), always to the farthest option.
--think
- Signal: "minimum number of ...", "maximum number of non-conflicting ...", "earliest finishing", "cheapest way" where each decision seems to have an obvious best. Sorting plus one pass is the typical shape.
- Decide the greedy criterion first, and then try to break it with a small counterexample. If you find one in a few minutes, switch to dynamic programming (it checks all choices and keeps the best, so it is correct where greedy fails).
- The two standard proofs are the exchange argument (swap an optimal solution's choice for yours without making it worse) and "greedy stays ahead" (show that after every step your partial answer is at least as good as any other strategy's).
- Typical greedy problems: interval scheduling, Huffman coding, fractional knapsack, minimum spanning tree (Kruskal and Prim), Dijkstra, jump game, task scheduling by deadlines.
- Pitfalls: choosing a criterion that sounds natural but is wrong (coins 4, 3, 1 above), forgetting ties, and forgetting to re-sort or re-heap when the best candidate changes after each step.
--cost
Usually `O(n log n)` for the sort or the heap, then `O(n)` for the pass. Space `O(1)` to `O(n)`.
--java
// minimum jumps to reach the last index; a[i] = longest jump from i. -1 if impossible.
static int minJumps(int[] a) {
    int jumps = 0, curEnd = 0, farthest = 0;
    for (int i = 0; i < a.length - 1; i++) {
        farthest = Math.max(farthest, clamp(i + a[i], 0, a.length - 1));   // best place reachable, capped at the end
        if (i == curEnd) {                         // must jump now: take the farthest option
            if (farthest <= i) return -1;          // stuck
            jumps++;
            curEnd = farthest;
        }
    }
    return jumps;
}

### exchange
--idea
An exchange argument is a way to prove that a greedy choice is safe. Take any best solution you can imagine. If it does not already start with the greedy choice, swap two things around so that it does, and show the swap does not make the answer worse. Then the greedy choice is part of some best solution, and you can lock it in and repeat on what is left.
Picture a queue at a bank where each customer has a service time and an impatience weight. If a slower, less impatient customer stands ahead of a quicker, more impatient one, swapping just those two neighbours cannot hurt the total and may help. Keep swapping neighbours and you reach one fixed order, the greedy order. Everyone else is unaffected by a swap of two neighbours, so only the pair's cost has to be compared.
--build
1. State the greedy rule you want to prove as an ordering ("do jobs in this order").
2. Assume an optimal solution that is not in greedy order. Then somewhere two adjacent items are in the wrong order relative to the rule. Call them `x` then `y`, where the rule says `y` should come first.
3. Compute the cost of just those two in both orders. Everything before them and after them is the same in both, so ignore it.
4. Show `cost(y then x) <= cost(x then y)`. Swapping is no worse.
5. Repeat the swap. Each swap removes one wrong-order pair, so after finitely many swaps the order is fully greedy and the cost is still optimal. So greedy is optimal.
6. Worked example (code below): jobs with time `t` and weight `w`, minimise the sum of `w * finish time`. For two neighbours starting at time `T`, order `x, y` costs `w_x (T + t_x) + w_y (T + t_x + t_y)`. Order `y, x` costs `w_y (T + t_y) + w_x (T + t_y + t_x)`. The difference is `w_y t_x` versus `w_x t_y`. So put `x` first when `t_x / w_x < t_y / w_y`, that is `t_x * w_y < t_y * w_x`.
7. Sort by that comparison and add up the cost.
8. In code, step 7's comparison is written with the piece `compare(t_x * w_y, t_y * w_x)`. It returns a negative number when `x` must come first. The cross products fit in an `int` when times and weights are up to about 40000; use `long` versions beyond that.
--think
- Signal: a problem about the best order of items (jobs, files, customers) or a choice among options where a pairwise comparison decides which goes first. Sorting with a custom comparator is the tell.
- To find the rule, do the two-neighbour swap on paper: write the cost for `x, y` and for `y, x`, then cancel everything that is the same. What is left is the comparison to sort by. This is more reliable than guessing.
- The comparator must be a consistent total order. Use cross multiplication (`t_x * w_y` against `t_y * w_x`) instead of dividing, to avoid floating point errors and zero division, but watch overflow: use `long`.
- If you cannot make the swap work (the pair cost depends on other items), the greedy is probably wrong. Try a different rule or use dynamic programming.
- Famous cases: shortest job first (all weights equal, so sort by time), interval scheduling by earliest end, Huffman coding, scheduling with deadlines, and arranging numbers to form the largest concatenation (compare `a+b` with `b+a`).
- Pitfalls: proving the swap for only one case of ties, a comparator that is not transitive, and forgetting that the argument is about adjacent items only (which is enough).
--cost
`O(n log n)` for the sort. Space `O(n)`.
--java
// jobs[i] = {time, weight}. Minimum possible sum of weight * finishing time.
static long minWeightedCompletion(int[][] jobs) {
    int[][] order = jobs.clone();
    // x goes before y when t_x / w_x < t_y / w_y, written without division
    Arrays.sort(order, (x, y) -> compare(x[0] * y[1], y[0] * x[1]));   // piece: -1, 0 or 1 (times and weights up to about 40000, so products fit an int)
    long time = 0, total = 0;
    for (int[] job : order) {
        time += job[0];                 // this job finishes at `time`
        total += time * job[1];
    }
    return total;
}

### intervals
--idea
Interval scheduling asks: given many time slots, each with a start and an end, what is the largest number you can attend if no two may overlap? The greedy answer is wonderfully short: always pick the interval that ends earliest among those that still fit. It leaves the most room for everything after it.
Why ending early is the right thing to optimise: the rest of the day is a smaller copy of the same problem starting from your chosen end time. Any other first choice that also fits ends no earlier, so it leaves the same amount of time or less. Swapping it for the earliest-ending one never loses an interval (this is an exchange argument).
--build
1. Sort the intervals by end time (break ties by anything, for example start time).
2. Keep `lastEnd`, the end of the last chosen interval, starting at minus infinity. Keep `count = 0`.
3. For each interval in order: if its start is at least `lastEnd` (it does not overlap, touching at a single point is allowed here), choose it: `count++` and `lastEnd = end`.
4. Otherwise skip it.
5. The answer is `count`. The minimum number you must remove to make the rest non-overlapping is `n - count`.
6. Variation for "minimum number of rooms or machines": sort starts and ends separately and sweep, or keep a min-heap of room end times (see sweep line).
7. Step 1 sorts with the piece `compare` applied to the two end times.
--think
- Signal: meetings, jobs, tasks with start and end, "attend as many as possible", "remove the fewest to avoid overlap", "fewest points that touch every interval" (sort by end, place a point at each end that is not yet covered).
- Decide what the greedy key is. Earliest end is correct for "maximum count". Earliest start, shortest length and fewest conflicts all have easy counterexamples, so do not use them. Try a tiny case: `[1,10], [2,3], [4,5]`: earliest start picks the long one and loses.
- If intervals have weights (pick the maximum total value), greedy fails. Use dynamic programming: sort by end, and `dp[i]` is the best using the first `i`, with binary search to find the last compatible interval.
- Decide whether touching intervals (`end == start`) count as overlapping. Use `>=` or `>` accordingly. It matters.
- Related: the sweep line handles "how many overlap at once", and a heap handles "assign to rooms".
- Pitfalls: sorting by start instead of end, comparing against the wrong variable, and overflow when subtracting large coordinates.
--cost
`O(n log n)` for the sort, `O(n)` for the pass. Space `O(1)` beyond the sort.
--java
// intervals[i] = {start, end}. Largest number of intervals with no overlap (touching is fine).
static int maxNonOverlap(int[][] intervals) {
    int[][] sorted = intervals.clone();
    Arrays.sort(sorted, (x, y) -> compare(x[1], y[1]));   // piece: earliest end first
    int count = 0;
    long lastEnd = Long.MIN_VALUE;
    for (int[] iv : sorted) {
        if (iv[0] >= lastEnd) {            // fits after the last chosen one
            count++;
            lastEnd = iv[1];
        }
    }
    return count;
}

        if start >= last_end:              # fits after the last chosen one
            count += 1
            last_end = end
    return count

### huffman
--idea
Huffman coding gives every symbol a binary code so that frequent symbols get short codes and rare ones get long codes, and the total length of the encoded message is as small as possible. No code is the beginning of another code (a prefix code), so you can decode a stream of bits from left to right without any separators. It is Morse code done properly.
Build it by repeatedly taking the two least frequent items and gluing them into one combined item whose frequency is their sum. Keep going until one item remains. This glued structure is a binary tree; going left adds a `0`, going right adds a `1`. The rare items were glued first, so they sit deepest and have the longest codes.
--build
1. Put every symbol in a min-heap keyed by frequency. Each entry is a tree node (initially a leaf for one symbol).
2. While the heap has more than one node: remove the two smallest nodes `a` and `b`. Make a new node with `left = a`, `right = b` and frequency `a + b`. Push it back.
3. The last node is the root of the code tree.
4. Walk the tree from the root, appending `0` when going left and `1` when going right. The string at a leaf is the code of that symbol.
5. A single symbol is a special case: give it the code `0` (a tree with only a root would give an empty code).
6. In the code, nodes `0..n-1` are the leaves, and new nodes get ids `n, n + 1, ...`. The heap holds pairs (frequency, id). Equal frequencies are broken by id, so the result is the same each time.
7. Total encoded length is the sum over all symbols of `frequency * code length`, which also equals the sum of every merged frequency.
--think
- Signal: "minimise the total cost of merging items where each merge costs the sum of the two" (merging files, ropes, stones): that is exactly Huffman, and the answer is the sum of all merge costs. Also compression, and "build the cheapest binary tree for given weights".
- Why the greedy is right: the two least frequent symbols can be assumed to be siblings at the deepest level (exchange argument: if a more frequent symbol were deeper, swap them and the total only drops). Merge them into one item and the rest is a smaller instance of the same problem.
- The code is not unique (ties and left/right choices), but its total length is. Compare total lengths, not strings, when testing.
- Huffman is optimal for symbol-by-symbol prefix codes. Methods that code groups of symbols (arithmetic coding, LZ) can do better overall.
- Related: the heap makes it `O(n log n)`. If the frequencies are already sorted, two queues do it in `O(n)`.
- Pitfalls: not handling the single symbol, comparing nodes in the heap that cannot be compared (give a tie-break id), and forgetting that codes must be taken from the tree, not computed from frequencies directly.
--cost
Time `O(n log n)` with a heap, space `O(n)`.
--java
// freq[i] = frequency of symbol i. Returns one binary code string per symbol.
static String[] huffmanCodes(int[] freq) {
    int n = freq.length;
    String[] codes = new String[n];
    if (n == 0) return codes;
    if (n == 1) { codes[0] = "0"; return codes; }
    int[] left = new int[2 * n], right = new int[2 * n];
    PriorityQueue<long[]> pq = new PriorityQueue<>((x, y) ->
        x[0] != y[0] ? Long.compare(x[0], y[0]) : Long.compare(x[1], y[1]));   // frequency, then id
    for (int i = 0; i < n; i++) pq.add(new long[]{freq[i], i});
    int next = n;
    while (pq.size() > 1) {
        long[] a = pq.poll(), b = pq.poll();               // the two rarest
        left[next] = (int) a[1];
        right[next] = (int) b[1];
        pq.add(new long[]{a[0] + b[0], next++});
    }
    assign((int) pq.poll()[1], "", left, right, n, codes);
    return codes;
}

static void assign(int node, String code, int[] left, int[] right, int n, String[] codes) {
    if (node < n) { codes[node] = code; return; }          // a leaf
    assign(left[node], code + "0", left, right, n, codes);
    assign(right[node], code + "1", left, right, n, codes);
}

import heapq

def huffman_codes(freq):
    """freq[i] = frequency of symbol i. Returns one binary code string per symbol."""
    n = len(freq)
    if n == 0:
        return []
    if n == 1:
        return ["0"]
    left, right = [0] * (2 * n), [0] * (2 * n)
    heap = [(f, i) for i, f in enumerate(freq)]          # (frequency, id)
    heapq.heapify(heap)
    nxt = n
    while len(heap) > 1:
        fa, a = heapq.heappop(heap)                      # the two rarest
        fb, b = heapq.heappop(heap)
        left[nxt], right[nxt] = a, b
        heapq.heappush(heap, (fa + fb, nxt))
        nxt += 1
    codes = [""] * n

    def assign(node, code):
        if node < n:                                     # a leaf
            codes[node] = code
            return
        assign(left[node], code + "0")
        assign(right[node], code + "1")

    assign(heap[0][1], "")
    return codes

### fracknap
--idea
In the fractional knapsack you have a bag with a weight limit and items that each have a value and a weight, and you may take part of an item (half a sack of rice is worth half as much). The goal is the most total value. The answer is the cleanest greedy there is: take items in order of value per unit of weight, best ratio first, until the bag is full.
It works because you are paying for weight and buying value, so you want the best "price per kilo" first. Taking a fraction of the last item lets you fill the bag exactly, so there is never wasted room. Compare this with the 0/1 knapsack (items cannot be split), where this greedy fails and dynamic programming is needed.
--build
1. For each item compute the ratio `value / weight` (the value you get per unit of capacity).
2. Sort items by ratio, largest first. To avoid decimal errors, compare `v1 * w2` with `v2 * w1` instead of dividing.
3. Keep `remaining = capacity` and `total = 0.0`.
4. For each item in order: if the whole item fits (`w <= remaining`), take it all: `total += v`, `remaining -= w`.
5. Otherwise take the fraction that fits: `total += v * remaining / w`, then stop (the bag is full).
6. Return `total`.
7. Step 2's cross multiplication is the piece `compare(v_y * w_x, v_x * w_y)`: it is negative when `x` has the better ratio. Products fit an `int` for values and weights up to about 40000.
--think
- Signal: "items you can split", "liquids", "take any fraction", "continuous" resources, where a single linear rule (value per weight) ranks all choices. If the statement says whole items only, it is not this problem.
- Proof (exchange): suppose an optimal answer takes some of a lower-ratio item while a higher-ratio item is not used up. Move a little weight from the low to the high item. The value goes up or stays the same, so the optimum has no such slack, which gives the sorted order.
- If items must be whole: do not use this. Use dynamic programming (knapsack). Greedy by ratio on whole items can be arbitrarily bad: capacity 10, items (weight 6, value 6) and (weight 5, value 5), (weight 5, value 5)... by ratio all tie and the choice matters.
- Many "assign resources" problems are this in disguise: pour the most valuable liquid first, buy the cheapest per unit first.
- Pitfalls: sorting by value or by weight alone, dividing by zero when a weight is 0 (treat as free value), using integer division when you need a fraction, and stopping the loop without handling the partial last item.
--cost
Time `O(n log n)` for the sort. Space `O(1)` extra.
--java
// items[i] = {value, weight} with weight > 0. Best total value, parts of items allowed.
static double fractionalKnapsack(int[][] items, int capacity) {
    int[][] sorted = items.clone();
    // higher value per weight first: v_x / w_x > v_y / w_y, compared by cross multiplication
    Arrays.sort(sorted, (x, y) -> compare(y[0] * x[1], x[0] * y[1]));   // piece; products fit an int for values and weights up to about 40000
    double total = 0;
    int remaining = capacity;
    for (int[] it : sorted) {
        if (remaining == 0) break;
        int take = Math.min(remaining, it[1]);          // all of it, or whatever room is left
        total += (double) it[0] * take / it[1];
        remaining -= take;
    }
    return total;
}

### divide
--idea
Divide and conquer solves a big problem by splitting it into smaller pieces of the same kind, solving each piece on its own (usually by the same method, recursively), and then combining the pieces' answers. Merge sort is the standard picture: cut the list in half, sort each half, then merge two sorted halves into one sorted list. The cutting is easy, the real work is in the combine step.
The gain comes from balance. Halving `n` times leaves a tower of only `log n` levels, and if the combine step at each level costs about `n` in total, the whole thing costs `n log n`. The combine step is also a good place to count things for free: while merging two sorted halves you can count how many pairs across the halves are out of order.
--build
1. Define the problem on a range `[lo, hi)` of the input and decide what the function returns for that range (here: the number of out-of-order pairs inside the range, and the range itself left sorted).
2. Base case: a range of 0 or 1 item. Return the trivial answer.
3. Split at `mid = (lo + hi) / 2`. Recursively solve `[lo, mid)` and `[mid, hi)`.
4. Combine: both halves are now sorted, so merge them with two pointers `i` (left half) and `j` (right half).
5. While merging, whenever the right item `a[j]` is strictly smaller than `a[i]`, it is smaller than every remaining left item too, so it forms `mid - i` inversions (pairs `x` before `y` with `x > y`). Add that to the count. Equal items are not inversions, so take the left one on ties.
6. Copy the merged result back into the array so that the parent sees a sorted range.
7. Total = left count + right count + cross count.
8. Step 3's split point is the piece `mid(lo, hi)`, which cannot overflow.
--think
- Signal: the problem splits cleanly in two (halves of an array, quadrants, left and right of a median) and the answer for the whole can be built from the answers for the halves plus the pairs that cross the middle. Counting inversions, closest pair of points, maximum subarray, merge sort, fast Fourier transform and "how many pairs `i < j` with some relation" are typical.
- Decide what the recursion returns, and what state (sortedness, a summary) each half must hand back to make the combine step cheap. A sorted half is the usual gift.
- Count the cost with a recurrence: `T(n) = 2 T(n/2) + O(n)` gives `O(n log n)`; `T(n) = 2 T(n/2) + O(1)` gives `O(n)`. If the combine is `O(n^2)`, you gained nothing.
- Related: when the recursion needs to count pairs with extra conditions, see CDQ divide and conquer; when subproblems overlap, you want dynamic programming rather than splitting; when only one half is needed, it is binary search.
- Pitfalls: counting inversions with `<=` versus `<` (ties), overflow (the count can reach about `n^2 / 2`, so use `long`), allocating new arrays at every level (use one scratch array), and `(lo + hi)` overflow for huge indices.
--cost
Time `O(n log n)`. Space `O(n)` for the scratch array plus `O(log n)` recursion.
--java
// number of pairs i < j with a[i] > a[j]
static long countInversions(int[] a) {
    int[] b = a.clone();                                  // sort a copy
    return sortCount(b, new int[b.length], 0, b.length);
}

// sorts a[lo..hi) and returns the inversions inside it
static long sortCount(int[] a, int[] tmp, int lo, int hi) {
    if (hi - lo < 2) return 0;                            // base case
    int m = mid(lo, hi);                                  // piece
    long inv = sortCount(a, tmp, lo, m) + sortCount(a, tmp, m, hi);
    int i = lo, j = m, k = lo;
    while (i < m || j < hi) {                           // merge the two sorted halves
        if (j >= hi || (i < m && a[i] <= a[j])) tmp[k++] = a[i++];
        else {
            inv += m - i;                               // a[j] jumps over every remaining left item
            tmp[k++] = a[j++];
        }
    }
    System.arraycopy(tmp, lo, a, lo, hi - lo);
    return inv;
}

### bits
--idea
A whole number is stored as a row of switches, each either on (1) or off (0). Bit manipulation means reading and changing those switches directly. The number 13 is `1101`: the switches for 8, 4 and 1 are on. A single integer can therefore hold a small set (switch `i` on means "item `i` is in the set") and operations on the whole set take one instruction.
The tools are shifts and the three logic operators. `1 << i` makes a number with only switch `i` on. `x & m` keeps only the switches that are on in both (intersection), `x | m` keeps those on in either (union), and `x ^ m` keeps those on in exactly one. With these you can test, set, clear and flip any switch, and combine whole sets at once.
--build
1. Number the switches from `0` at the right. Switch `i` stands for the value `2^i`.
2. Read switch `i`: shift it to the bottom and look at it, `(x >> i) & 1`. This is the piece `getBit(x, i)`.
3. Turn switch `i` on: `x | (1 << i)`, the piece `setBit`. Turn it off: `x & ~(1 << i)`, the piece `clearBit`.
4. Flip switch `i` (on becomes off and the reverse): `x ^ (1 << i)`. In `flipBit` below it is written with `getBit`, `clearBit` and `setBit` so each step is visible.
5. Count the switches that are on with the piece `popcount(x)`. `hammingDistance(a, b)` calls it on `a ^ b`, because `^` leaves a 1 exactly where the two numbers differ.
6. Set tests: `a` is a subset of `b` exactly when `(a & b) == a`. The union is `a | b`, the intersection `a & b`, and "everything except `a`" within `n` items is `((1 << n) - 1) ^ a`.
7. To build a mask from a list of positions, start from `0` and call `setBit` for each one (`maskOf`).
--think
- Signal: a small set of items (`n <= 20` or so) where you need to remember which are chosen, "visited" flags for a search, states of switches or lamps, or a yes/no table that must be copied or compared quickly. Also anything about parity, powers of two, or "the binary representation".
- Decide how many bits you need. 32 bits fit an `int`. For up to 63 switches use a 64-bit `long` and write `1L << i` (plain `1 << i` is a 32-bit number and silently wraps).
- A mask is a way to turn a set into a number, so it can be an array index or a hash key. This is the base of bitmask dynamic programming and of looping over all subsets.
- Related: bit tricks (short expressions like `x & (x - 1)`), enumerating subsets, XOR tricks, Gray code. If you need more than 64 switches, use a `bitset` (C++) or `BitSet` (Java), which pack many bits into an array.
- Pitfalls: operator precedence (in many languages `x & 1 == 0` means `x & (1 == 0)`, so always add brackets), shifting by an amount equal to or larger than the word size (undefined in C++), using `>>` on a negative number (it keeps the sign; in Java use `>>>` for a logical shift), and numbering switches from 1 in the problem but from 0 in your code.
--cost
Each single-bit operation is `O(1)`. Counting set bits is `O(1)` with a hardware instruction. A mask of `n` bits takes `n / 8` bytes, so `n` up to 20 gives about a million possible masks.
--java
// flip bit i: turn it off if it is on, on if it is off
static int flipBit(int x, int i) {
    return getBit(x, i) ? clearBit(x, i) : setBit(x, i);
}

// is every item of set a also in set b?
static boolean isSubset(int a, int b) {
    return (a & b) == a;                       // intersecting with b must lose nothing
}

static int hammingDistance(int a, int b) {
    return popcount(a ^ b);                    // ^ is 1 exactly where the bits differ
}

### bittricks
--idea
Bit tricks are short expressions that do something useful to all the bits of a number at once. They exist because of a few facts about how binary numbers behave. The best known: `x & -x` leaves only the lowest switch that is on. Subtracting 1 from a number flips its lowest on switch and all the switches below it, so `x & (x - 1)` switches off the lowest on switch.
Think of a row of lamps counted in binary. Adding one flips a run of lamps at the right end. Knowing that, you can find the lowest lamp, test whether exactly one lamp is on (a power of two), and count the lamps by peeling them off one at a time, all without a loop over every position.
--build
1. The lowest set bit: `lowbit(x) = x & -x`. In two's complement (how computers store negatives) `-x` is "flip all bits then add 1", which leaves the lowest on switch in place and flips everything above it. So `x & -x` keeps just that one. Example: `12 = 1100`, `lowbit = 0100 = 4`.
2. Remove the lowest set bit: `x - lowbit(x)`, the same as `x & (x - 1)`.
3. Power of two test: a power of two has exactly one switch on, so removing it leaves 0. The piece `isPowerOfTwo(x)` is `x > 0 && (x & (x - 1)) == 0`. The `x > 0` handles zero.
4. Count the on bits of every number up to `n` with dynamic programming: `bits[i] = bits[i - lowbit(i)] + 1`, because removing the lowest switch leaves a smaller number that is already counted (`countBitsUpTo`).
5. Walk over the on bits of `x` from lowest to highest by repeating "take `lowbit`, remove it" until `x` is zero (`bitValues`). The cost is the number of on bits, not the word size.
6. Round up to a power of two: if `isPowerOfTwo(x)` already, return `x`; otherwise double a `p` from 1 until it reaches `x` (`roundUpPow2`).
--think
- Signal: statements about "the lowest set bit", "number of 1 bits", "is a power of two", "iterate over the bits of a mask", or a data structure whose indexes use the lowest bit (Fenwick tree jumps by `i & -i`).
- Decide whether you can reduce the work to the on bits only. A loop that peels off the lowest bit runs once per on bit, which is much faster than checking all 32 or 64 positions when the mask is sparse.
- Related: for just counting bits the library functions (`popcount`, `Integer.bitCount`, `__builtin_popcount`) are best. The `lowbit` pattern wins when you need to act on each bit, as in Fenwick trees and bitmask DP.
- Famous uses: Fenwick tree (update `i += lowbit(i)`, query `i -= lowbit(i)`), subset sum over masks, checking a number is a power of two, finding the single different bit between two numbers (`lowbit(a ^ b)`).
- Pitfalls: `isPowerOfTwo(0)` must be false (the `x > 0` check), `x & -x` on the smallest negative int overflows in some languages, and mixing signed and unsigned in C++ makes `-x` huge but still correct for `lowbit` on `unsigned`.
--cost
`lowbit`, power of two and clearing the lowest bit are `O(1)`. `countBitsUpTo(n)` is `O(n)`. Walking over the set bits of `x` is `O(popcount(x))`.
--java
// bits[i] = number of 1 bits in i, for i from 0 to n
static int[] countBitsUpTo(int n) {
    int[] bits = new int[n + 1];
    for (int i = 1; i <= n; i++)
        bits[i] = bits[i - lowbit(i)] + 1;     // drop the lowest set bit, add one for it
    return bits;
}

// the values of the set bits of x, lowest first (12 gives 4 then 8)
static List<Integer> bitValues(int x) {
    List<Integer> out = new ArrayList<>();
    while (x != 0) {
        int low = lowbit(x);
        out.add(low);
        x -= low;                              // remove it and continue
    }
    return out;
}

### subsetenum
--idea
Enumerating subsets means visiting every subset of a set of `n` items exactly once. With a bit mask this is a plain counting loop: write each number from `0` to `2^n - 1` in binary, and let the switches that are on be the chosen items. Mask `0` is the empty set, mask `2^n - 1` is everything. There is no recursion and no undo, just a loop.
The second pattern is visiting only the subsets of one particular mask, called its submasks. The loop `sub = (sub - 1) & mask` steps through them from the biggest to the smallest. Subtracting 1 turns the lowest on switch off and all below it on, and the `& mask` throws away switches that are not allowed. Together they visit each submask once, in decreasing order.
--build
1. All subsets: `for mask = 0; mask < (1 << n); mask++`. The items in the subset are the positions of the on bits.
2. To get something about the subset (such as its sum) without looping over `n` bits each time, build it from a smaller mask: `sum[mask] = sum[mask without its lowest bit] + a[lowest bit]`. The mask `mask & (mask - 1)` is smaller than `mask`, so it is already filled in (`allSubsetSums`).
3. The lowest bit's position is the number of trailing zeros of `mask` (`numberOfTrailingZeros` in Java, `__builtin_ctz` in C++, `(mask & -mask).bit_length() - 1` in Python).
4. Submasks of `mask`: call the piece `submasks(mask)`. It starts with `sub = mask` and repeats `sub = (sub - 1) & mask` while `sub > 0`, so it lists every non-empty submask. The empty set is not included, handle it separately.
5. Use `submaskSums` to list the sums of all non-empty subsets inside one mask by looking each submask up in the table from step 2.
6. Looping over the submasks of every mask costs `3^n` in total, because each of the `n` items is either not in the mask, in the mask but not the submask, or in both. `countPairs` counts this with the piece.
--think
- Signal: `n <= 20` (all subsets) or `n <= 15` (all submasks of all masks), and each subset needs a small check: sum, validity, whether it is independent. "Choose any subset such that ..." with tiny `n` is a mask loop.
- Decide what you store per mask. Many problems fill a table `dp[mask]` in increasing mask order, because every submask of `mask` is a smaller number and is therefore already computed.
- The `3^n` pattern appears in "split the set into two groups" dynamic programming: `dp[mask] = best over submasks sub of dp[sub] + dp[mask ^ sub]`. At `n = 15` that is 14 million steps, fine; at `n = 20` it is 3.5 billion, too slow.
- If `n` is up to 40, use meet in the middle. If you only need sums over all subsets of every mask (a "zeta transform" or sum over subsets) there is an `O(n 2^n)` method, which is faster than looping the submasks.
- Pitfalls: `1 << n` overflows an `int` when `n = 31` (use `1L`), forgetting the empty submask (the loop stops at `sub > 0`), and allocating `2^n` entries when `n` is larger than about 25 (memory).
--cost
All subsets: `O(2^n)` masks, with the incremental sum `O(1)` each. All submasks of all masks: `O(3^n)`. Space `O(2^n)` for a table.
--java
// sum[mask] = total of the items chosen by mask; each entry costs O(1)
static long[] allSubsetSums(int[] a) {
    int n = a.length;
    long[] sum = new long[1 << n];
    for (int mask = 1; mask < (1 << n); mask++) {
        int low = Integer.numberOfTrailingZeros(mask);     // position of the lowest item
        sum[mask] = sum[mask & (mask - 1)] + a[low];       // the rest is already computed
    }
    return sum;
}

### gray
--idea
Gray code is a way to list all the `n`-bit numbers so that each one differs from the next in exactly one bit. In ordinary counting, going from 3 (`011`) to 4 (`100`) flips three bits at once. In Gray order the neighbours always differ by a single flip, like a combination lock that changes one dial at a time. The list is also a loop: the last entry differs from the first by one bit.
The formula is short: the Gray code of `i` is `i ^ (i >> 1)`. Each output bit is the XOR of the matching input bit and the one above it. Another view is the mirror rule: take the list for `n - 1` bits, write it again in reverse below it, and put a `0` in front of the first half and a `1` in front of the second half.
--build
1. For `i` from `0` to `2^n - 1` compute `g[i] = i ^ (i >> 1)`. That is the whole list (`grayCodes`).
2. Why neighbours differ by one bit: going from `i` to `i + 1` flips a run of low bits (a trailing block of ones becomes zeros and the zero above becomes one). The XOR with the shifted copy cancels the run so that only one bit of the result changes.
3. To go back from a Gray code `g` to the plain number `b`, each bit of `b` is the XOR of all bits of `g` at that position and above. Walk from the top bit down keeping a running XOR `prev`. At each position update `prev ^= bit of g`, and if `prev` is 1 turn that bit on in `b` (`fromGray`). It reads bits with the piece `getBit` and writes them with `setBit`.
4. To check a list, count the bits of `g[i] ^ g[i + 1]` for every neighbour pair (also `g[last]` with `g[0]`). The count is always 1, which is what step 2 proves.
5. To list the bit that flips at step `i`, take the position of the lowest set bit of `i + 1`.
--think
- Signal: you must visit every state of a set of switches (lamps, subsets, a combination lock) by changing one thing at a time. Also "order the numbers so that adjacent ones differ by a bit", rotary encoders, and subsets enumerated so that each step adds or removes one item (so a running sum changes in `O(1)` per step).
- Decide whether you need the order or just the property. If only the first `k` codes or a cyclic order matter, the formula gives each entry independently, no state needed.
- The step-by-one-flip order lets you keep a running value (sum, count) and update it with a single add or subtract, which is faster than recomputing for each subset.
- Related: enumerating subsets (plain mask order), bit tricks, and the Tower of Hanoi, whose move sequence follows the same pattern.
- Pitfalls: confusing Gray code with plain binary, shifting a negative number (use unsigned or keep `i` non-negative), and forgetting that decoding needs a running XOR from the top, not a single shift.
--cost
Each code is `O(1)` to produce, so `O(2^n)` for the whole list. Decoding is `O(n)` per number.
--java
// all 2^n Gray codes in order
static int[] grayCodes(int n) {
    int[] g = new int[1 << n];
    for (int i = 0; i < g.length; i++)
        g[i] = i ^ (i >> 1);                   // each bit is the XOR of itself and the bit above
    return g;
}

// turn a Gray code with the given number of bits back into the plain number
static int fromGray(int g, int bits) {
    int b = 0, prev = 0;
    for (int i = bits - 1; i >= 0; i--) {      // from the top bit down
        prev ^= getBit(g, i) ? 1 : 0;          // running XOR of the Gray bits seen so far
        if (prev == 1) b = setBit(b, i);
    }
    return b;
}

### xortricks
--idea
XOR (written `^`) compares two bits and gives 1 when they differ. It has three properties that make it a favourite: `x ^ x = 0` (a value cancels itself), `x ^ 0 = x` (zero changes nothing), and the order does not matter. So if you XOR a list in which every value appears twice except one, all the pairs vanish and only the odd one out remains. It is like a light switch: flipping it twice puts it back.
XOR is also addition without carrying, done independently on every bit. That lets you split a set of numbers into groups by a single bit, and it is its own inverse: if `c = a ^ b` then `a = c ^ b`. This is how a value can be hidden and recovered, and how two values can be swapped with no temporary.
--build
1. One number appears once, all others twice: XOR everything. Pairs cancel, the single remains (`findSingle`).
2. A missing number from `0..n`: XOR all the indices `0..n` with all the array values. Every present number appears twice and cancels, the missing one remains (`missingNumber`).
3. Two numbers `p` and `q` appear once, all others twice. XOR everything to get `x = p ^ q`. Since `p != q`, `x` is not zero and has some bit that is on.
4. Find the lowest such bit with the piece `getBit(x, k)` in a loop over `k`. At that bit `p` and `q` differ: one has it on, the other off.
5. Split the array in two groups by that bit, again using `getBit(v, k)`. Each group contains exactly one of `p`, `q`, and the pairs are still together inside a group. XOR the group where the bit is on to get `p`, then `q = x ^ p` (`twoSingles`).
--think
- Signal: "every element appears twice except one (or two)", "find the missing number", "XOR of a range", "XOR of subarrays", or operations that are their own undo (toggle). Pairs cancelling is the sign.
- Decide whether prefix XOR helps: define `px[i] = a[0] ^ ... ^ a[i-1]`, then the XOR of any subarray `a[l..r]` is `px[r + 1] ^ px[l]`, just like prefix sums (XOR is the "minus" of itself).
- XOR also solves "maximum XOR of two numbers" (with a binary trie) and the game of Nim (the first player wins exactly when the XOR of the pile sizes is not zero).
- Limits: cancelling works only for an even number of copies. If values appear three times with one appearing once, use a per-bit count modulo 3. If the "pairs" are not pairs at all (arbitrary duplicates), use a hash map.
- Pitfalls: the idea fails when the same value could appear an odd number of times for other reasons, `x ^ y` has lower precedence than `==` in C++ and Java (always bracket), and negative numbers are fine because XOR works on the raw bits.
--cost
Time `O(n)` for one pass (two passes for `twoSingles`). Space `O(1)`.
--java
// every value appears twice except one: return that one
static int findSingle(int[] a) {
    int x = 0;
    for (int v : a) x ^= v;                    // pairs cancel
    return x;
}

// the numbers 0..n with one missing, given as an array of length n
static int missingNumber(int[] a) {
    int x = a.length;                          // include n itself
    for (int i = 0; i < a.length; i++) x ^= i ^ a[i];
    return x;
}

// two values appear once, all others twice: return them in increasing order
static int[] twoSingles(int[] a) {
    int x = 0;
    for (int v : a) x ^= v;                    // x = p ^ q, which is not zero
    int k = 0;
    while (!getBit(x, k)) k++;                 // a bit where p and q differ
    int p = 0;
    for (int v : a) if (getBit(v, k)) p ^= v;  // this group holds exactly one of them
    int q = x ^ p;
    return new int[]{Math.min(p, q), Math.max(p, q)};
}

### meet
--idea
Meet in the middle splits a search that is too big for brute force into two halves that are each small, solves each half separately, and then joins the two answers cleverly. If a problem has `n = 40` items, trying all `2^40` subsets (a trillion) is hopeless, but each half of 20 items has only a million subsets. You list the subsets of each half and then match them up, which costs about `2^20` instead of `2^40`.
The matching works because the condition splits: "the total of the whole subset equals `target`" is the same as "left part sum + right part sum = `target`". So for each left sum you only need to look up whether the needed right sum exists. A hash map or a sorted list answers that lookup fast. The trick turns an `O(2^n)` search into about `O(2^(n/2))`.
--build
1. Split the items in two halves: the first `h = n / 2` items and the rest.
2. For each half, list the sum of every subset (`halfSums`). Loop `mask` over all subsets of the half. Use the piece `itemsIn(mask, m)` to get which items the mask picks, and add them up.
3. Store each half's sums in a map from sum to how many subsets give it. That is `2^(n/2)` entries at most.
4. For every sum `s` in the left map, the right half must supply `target - s`. Look it up in the right map.
5. Add `leftCount * rightCount` to the answer for each match. Counting this way includes the empty subset of either half, which is correct because a full subset may take nothing from one half.
6. For "does a subset sum exist" you can stop at the first match. For "closest to the target", keep the right sums in a sorted list and binary search for the nearest value.
7. The cost is `2^(n/2)` per half, plus the lookup, instead of `2^n`.
--think
- Signal: `n` around 30 to 45, too big for `2^n` but small enough for `2^(n/2)`. Typical: subset sum, "choose items with total weight at most W" (knapsack with huge weights), counting solutions of a small system, 4-sum, and "split the items so the difference is smallest".
- Decide whether the condition separates into a left part and a right part. If the two halves interact in a way that cannot be split (for example, the total depends on pairs of items from different halves), meet in the middle does not apply.
- Use a hash map when you need exact matches and a sorted list with binary search or two pointers when you need "at most" or "closest". Sorting both halves lets you sweep with two pointers in `O(2^(n/2))` after the sort.
- Alternatives: dynamic programming over sums is better when the target is small (`O(n * target)`), and bitmask dynamic programming is better when the structure is "visit each item once". Meet in the middle is the tool when values are large and `n` is medium.
- Related: the "four sum" problem uses the same idea with pairs, and bidirectional search in a graph meets in the middle between a start and a goal.
- Pitfalls: counting the empty subset by mistake (or leaving it out), sums too large for 32 bits (use `long`), an unbalanced split (`h` far from `n / 2` makes one side too large), and a hash map attacked by adversarial inputs (prefer a sorted array if that matters).
--cost
Time and space `O(2^(n/2))` times `n/2` for building the sums in this version. For `n = 40` that is about a million entries per half.
--java
// all subset sums of a[from..to), as a map: sum -> how many subsets give it
static Map<Long, Long> halfSums(long[] a, int from, int to) {
    int m = to - from;
    Map<Long, Long> res = new HashMap<>();
    for (int mask = 0; mask < (1 << m); mask++) {
        long s = 0;
        for (int i : itemsIn(mask, m)) s += a[from + i];   // piece: which items this mask picks
        res.merge(s, 1L, Long::sum);
    }
    return res;
}

// number of subsets (the empty one included) whose sum is exactly target
static long countSubsetsWithSum(long[] a, long target) {
    int h = a.length / 2;
    Map<Long, Long> left = halfSums(a, 0, h), right = halfSums(a, h, a.length);
    long total = 0;
    for (Map.Entry<Long, Long> e : left.entrySet())         // for each left sum, look up the partner
        total += e.getValue() * right.getOrDefault(target - e.getKey(), 0L);
    return total;
}

### coord
--idea
Coordinate compression replaces a set of huge or awkward values by small whole numbers that keep the same order. If an input contains values like `5`, `1000000000` and `-7`, you cannot use them as array positions. But only the order and equality of the values matter in many problems, so you can number them by rank: the smallest becomes `0`, the next `1`, and so on. Then every value is a small index you can use in an array, a Fenwick tree or a table.
It is like turning phone numbers into seat numbers: the numbers themselves were never the point, only who comes before whom. The catch is that distances are lost. If the real gap between two neighbouring values matters (a length), keep a table that maps each rank back to the original value.
--build
1. Collect all the values that will ever matter (for segments, both ends of every segment).
2. Call the piece `compress(values)`. It sorts the distinct values and replaces each value by its position in that sorted list. Equal values get equal ranks.
3. The ranks run from `0` to `k - 1`, where `k` is the number of distinct values. Use them as array indices of size `k`.
4. When real distances matter, rebuild the reverse map: `value[rank[i]] = original[i]`, so `value[j]` is the real coordinate of rank `j`.
5. Work on the small array (a difference array, a sweep, a Fenwick tree). A step from rank `j` to rank `j + 1` covers the real length `value[j + 1] - value[j]`.
6. Example (`unionLength`): add `+1` at the rank of each segment start and `-1` at the rank of each end, take a running total, and add up the real lengths of the steps where the total is positive. That is the length of the number line covered by at least one segment.
--think
- Signal: values up to `10^9` (or negative, or real numbers) but only `n` of them, and the algorithm needs to index by value: counting, Fenwick tree, segment tree, "how many smaller than", painting segments on a huge line.
- Decide first what has to be preserved: only order (ranks are enough), or order and distances (keep the reverse map), or also the gaps between points (add the neighbours `x - 1` and `x + 1` as extra points when the problem has cells, not just points).
- It is a standard first step for a sweep line and for offline queries: compress, then sweep. For sorting-based tasks like inversions it replaces the values with `0..k-1` before a Fenwick tree.
- The cost is a sort, so `O(n log n)`. If values are already small (below about `10^6`), just index by them directly and skip compression.
- Pitfalls: forgetting duplicates (ranks must be of the distinct values), compressing queries and data separately so the ranks do not match (compress everything together), and mixing the compressed and original values in one expression.
--cost
`O(n log n)` time for the sort, `O(n)` space. Each rank lookup afterwards is `O(1)`.
--java
// total length covered by the segments [l, r) on a huge number line; segs[i] = {l, r}
static long unionLength(int[][] segs) {
    int m = segs.length;
    int[] pts = new int[2 * m];
    for (int i = 0; i < m; i++) { pts[2 * i] = segs[i][0]; pts[2 * i + 1] = segs[i][1]; }
    int[] rank = compress(pts);                         // piece: each end becomes its rank
    int k = 0;
    for (int r : rank) k = Math.max(k, r + 1);          // number of distinct ends
    int[] value = new int[k];
    for (int i = 0; i < pts.length; i++) value[rank[i]] = pts[i];   // back from rank to coordinate
    int[] diff = new int[k + 1];
    for (int i = 0; i < m; i++) { diff[rank[2 * i]]++; diff[rank[2 * i + 1]]--; }
    long total = 0;
    int cover = 0;
    for (int j = 0; j + 1 < k; j++) {
        cover += diff[j];                               // how many segments cover step j
        if (cover > 0) total += (long) value[j + 1] - value[j];
    }
    return total;
}

### sweep
--idea
A sweep line imagines a vertical line moving across the plane (or a point moving along a number line) from left to right. Instead of looking at all objects at once, you process only the moments where something changes, called events, in order, and you keep a small summary of what is "active" right now. A road with roadworks is a good picture: as you drive, you only care when a work zone starts and when it ends.
The insight is that sorting the events turns a two-dimensional or overlapping problem into a one-dimensional pass. To find the most overlapping intervals, make an event `+1` at every start and `-1` at every end, sort them, and keep a running total. The largest the total ever gets is the answer.
--build
1. Decide what the events are. For intervals there are two per interval: a start (`+1`) and an end (`-1`), each stored as a pair `(time, change)`.
2. Sort the events. The piece `comparePairs` (`pair_key` in Python, `pairLess` in C++) orders pairs by the first value, then the second. With `change` as the second value, `-1` sorts before `+1` at the same time, so an interval ending at time 5 is closed before one starting at time 5 opens. That treats intervals as half open `[start, end)`.
3. Keep a running total `cur` of active intervals. Process events in order: `cur += change`.
4. After each event, record the answer you need (here `best = max(best, cur)`).
5. If the events carry more detail (heights in a skyline, rectangles), keep the active items in a structure that gives the best one quickly, such as a heap or a multiset, and remove items when their end event arrives.
6. If coordinates are huge, you only sort the `O(n)` event times, so no compression is needed beyond the sort.
--think
- Signal: intervals, rectangles, or points where "how many overlap", "is there a conflict", "total covered area or length", "closest pair", "skyline" or "meeting rooms" is the question. Anything that changes at known moments along one axis.
- Decide the axis to sweep along and what the events are. Then decide the tie-break at equal positions, because it decides whether touching counts as overlapping. This is the most common bug.
- Pick the active-set structure by the question: a counter for "how many", a heap for "the earliest end" or "the maximum height", a balanced tree (sorted set) for "the nearest neighbour", a Fenwick tree for "how many to my left".
- Related: interval scheduling (greedy), difference arrays (the sweep without sorting when coordinates are small), and offline queries (queries become events too).
- Pitfalls: a wrong tie-break at equal times, processing end events after start events (counts too high), forgetting that the answer can only change at events (so checking between them is pointless), and using `int` for large coordinate differences.
--cost
`O(n log n)` for sorting `2n` events, then `O(n)` for the pass (or `O(n log n)` with a heap or tree). Space `O(n)`.
--java
// most intervals that overlap at one moment; intervals[i] = {start, end}, half open [start, end)
static int maxOverlap(int[][] intervals) {
    int[][] ev = new int[2 * intervals.length][];
    for (int i = 0; i < intervals.length; i++) {
        ev[2 * i] = new int[]{intervals[i][0], +1};         // an interval opens
        ev[2 * i + 1] = new int[]{intervals[i][1], -1};     // an interval closes
    }
    Arrays.sort(ev, (x, y) -> comparePairs(x, y));          // piece: by time, then -1 before +1
    int cur = 0, best = 0;
    for (int[] e : ev) {
        cur += e[1];
        best = Math.max(best, cur);
    }
    return best;
}

### offline
--idea
Offline processing means you read all the queries first, and then answer them in an order you choose, instead of in the order they arrive. The answers are the same, but the right order can make each one far easier. Think of a postman who collects all the letters first and plans a route, rather than walking to each house the moment a letter is written.
A classic example: count the distinct values in many ranges `[l, r]` of an array. Sort the queries by their right end `r`, and sweep `r` from left to right. Keep a Fenwick tree (a structure for fast prefix sums with updates) holding a `1` at the last position where each value appeared. Then the number of distinct values in `[l, r]` is simply the sum of the tree over `[l, r]`, because every value in the range is counted once, at its latest position.
--build
1. Read all queries `(l, r)` and remember their original index `id`, so the answers can be put back in the original order.
2. Sort the query indices by `r`. The piece `sortIndices(rs)` does this: it returns the positions of the queries ordered by `r`, without moving the queries themselves.
3. Create a Fenwick tree `bit` of size `n`. The piece `add(i, v)` adds `v` at position `i` and updates the cells that cover it. You need a matching `prefixSum(i)`, written here because the piece set has only the update.
4. Sweep `r` from `0` to `n - 1`. Look up where the value `a[r]` last appeared (`last`). If it appeared before at `p`, call `add(p, -1)` to remove the old mark.
5. Call `add(r, +1)` to mark the new, latest position of this value, and remember `last[a[r]] = r`.
6. Answer every query whose right end is `r`: the distinct count is `prefixSum(r) - prefixSum(l - 1)`. Store it at the query's original index.
7. The invariant: after step 5 for `r`, the tree has exactly one mark for each distinct value in `a[0..r]`, at the last position of that value. Therefore the marks inside `[l, r]` are exactly the distinct values of that range.
--think
- Signal: many range or prefix queries, no updates between them, and the answer for a range is hard to compute directly but easy to maintain incrementally. Also "for each query, count elements less than `x` in `a[l..r]`", "number of pairs ... in a range".
- Decide which order makes the structure simple: sort by right end (maintain "latest position" data), by threshold value (add elements as the threshold grows, then ask how many are in the range), or by time.
- If the data can change, you need an online structure (segment tree, persistent tree) or Mo's algorithm with updates. Offline works only because you can see the future queries.
- Neighbours: Mo's algorithm also answers distinct-count queries offline, in `O((n + q) sqrt n)`; the Fenwick sweep is `O((n + q) log n)` and faster. Use Mo when the add and remove of an item are easy but there is no clean prefix structure.
- Pitfalls: forgetting to put the answers back in the original order, removing the old mark before adding the new one on the same position, off-by-one with `prefixSum(l - 1)` when `l = 0` (return `0`), and running a Fenwick tree with index `0` (the tree is 1-based inside).
--cost
`O((n + q) log n)` time: a sort of the queries, then `n` updates and `q` range queries. Space `O(n + q)`.
--java
static int n;                // size of the Fenwick tree; the piece add(i, v) uses n and bit
static long[] bit;

// the piece (shown here for reference; it uses the fields above):
//   static void add(int i, long v) { for (i++; i <= n; i += i & -i) bit[i] += v; }

static long prefixSum(int i) {                       // sum of positions 0..i
    long s = 0;
    for (i++; i > 0; i -= i & -i) s += bit[i];
    return s;
}

// queries[q] = {l, r}; returns the number of distinct values in a[l..r] for each query
static int[] distinctInRanges(int[] a, int[][] queries) {
    n = a.length;
    bit = new long[n + 1];
    int[] rights = new int[queries.length];
    for (int i = 0; i < rights.length; i++) rights[i] = queries[i][1];
    Integer[] order = sortIndices(rights);           // piece: queries ordered by right end
    int[] ans = new int[queries.length];
    Map<Integer, Integer> last = new HashMap<>();    // value -> latest position so far
    int next = 0;
    for (int r = 0; r < n; r++) {
        Integer prev = last.put(a[r], r);
        if (prev != null) add(prev, -1);             // piece: the old mark moves forward
        add(r, 1);                                   // piece: mark the latest position
        while (next < order.length && queries[order[next]][1] == r) {
            int id = order[next++];
            ans[id] = (int) (prefixSum(r) - prefixSum(queries[id][0] - 1));
        }
    }
    return ans;
}

def prefix_sum(i):

### mo
--idea
Mo's algorithm answers many range queries on an array by reordering them so that a single window `[curL, curR]` can slide from one query's range to the next with very little movement. When adding or removing one item at the end of the window is cheap (update a count, a distinct total), the cost of a query is just the distance the window has to travel. By sorting the queries cleverly, the total travel of all queries is about `n * sqrt(q)` instead of `n * q`.
The sorting rule: cut the positions into blocks of about the same size. Group the queries by the block that holds their left end `l`. Inside a block, sort by the right end `r`. Within one block the left end moves less than the block size per query, and the right end only moves forward, so over the whole block it travels at most `n`. With `n / block` blocks, the totals balance when `block` is about `n / sqrt(q)`.
--build
1. Read all queries `(l, r)` with their index `id` (both ends included). Offline only: you must know all queries first.
2. Choose the block size `block = max(1, n / sqrt(q))`, so that about `sqrt(q)` blocks exist.
3. Give each query a sort key: first `b = l / block`, then `r`. Use the odd-even trick: in odd blocks sort `r` in descending order (key `n - r`). The window then sweeps right in one block and left in the next with no wasted walk back. Combine into one number `b * (n + 1) + r` (or `n - r`).
4. Call the piece `sortIndices(key)` to get the query ids in that order, without moving the queries.
5. Keep the window `[curL, curR]` starting empty as `curL = 0, curR = -1`, plus the running answer (`distinct`) and a count table `cnt`.
6. For each query in order, move the window to `[l, r]` with four loops. Do the growing loops first, then the shrinking loops, so the counts never go negative: `while curL > l: curL--, add(a[curL])`, then `while curR < r: curR++, add(a[curR])`, then `while curL < l: remove(a[curL]), curL++`, then `while curR > r: remove(a[curR]), curR--`.
7. `add(x)`: `cnt[x]++`, and if it became `1`, `distinct++`. `remove(x)`: `cnt[x]--`, and if it became `0`, `distinct--`.
8. After the four loops the window equals the query, so `ans[id] = distinct`.
--think
- Signal: many range queries (`n, q` up to about `10^5`), no updates, the answer is a function of the multiset of values in the range, and adding or removing one value at the end changes the answer in `O(1)`. Distinct counts, sum of squares of frequencies, "how many values appear exactly `k` times".
- Decide first whether an add and a remove are both `O(1)`. If you can add but not remove (a maximum, say), use a rollback variant or a different method. If a clean prefix structure exists (prefix sums, offline with a Fenwick tree), prefer it: it is faster.
- The cost is `O((n + q) sqrt n)`, so at `10^5` that is about 30 million moves, fine. At `10^6` it is too slow without tuning.
- Choose the block size by the formula `n / sqrt(q)`; a fixed `sqrt(n)` also works. The right end `r` is only monotone inside a block, so the key must combine the block and `r`.
- Related: Mo with updates (adds a time dimension), Mo on trees (turns paths into ranges), offline Fenwick sweeps, and square root decomposition (online, with a block structure instead).
- Pitfalls: shrinking before growing (negative counts), values too large for the count array (compress first), using `l` instead of the block for the key, sorting with a slow comparator on 2D keys (the key trick above avoids it), and answering in sorted order without writing back to `id`.
--cost
Time `O((n + q) sqrt n)` for the window moves plus `O(q log q)` for the sort. Space `O(n + q)`.
--java
// number of distinct values in a[l..r] for each query {l, r}; values are non-negative ints
static int[] moDistinct(int[] a, int[][] queries) {
    int n = a.length, q = queries.length;
    int block = Math.max(1, (int) (n / Math.sqrt(Math.max(1, q))));
    int[] key = new int[q];
    for (int i = 0; i < q; i++) {
        int b = queries[i][0] / block, r = queries[i][1];
        key[i] = b * (n + 1) + (b % 2 == 0 ? r : n - r);     // odd blocks go right to left
    }
    Integer[] order = sortIndices(key);                       // piece: query ids in Mo order
    int maxV = 0;
    for (int x : a) maxV = Math.max(maxV, x);
    int[] cnt = new int[maxV + 1], ans = new int[q];
    int curL = 0, curR = -1, distinct = 0;
    for (int id : order) {
        int l = queries[id][0], r = queries[id][1];
        while (curL > l) { curL--; if (cnt[a[curL]]++ == 0) distinct++; }   // grow first
        while (curR < r) { curR++; if (cnt[a[curR]]++ == 0) distinct++; }
        while (curL < l) { if (--cnt[a[curL]] == 0) distinct--; curL++; }   // then shrink
        while (curR > r) { if (--cnt[a[curR]] == 0) distinct--; curR--; }
        ans[id] = distinct;
    }
    return ans;
}

def mo_distinct(a, queries):
    """Number of distinct values in a[l..r] for each query (l, r); values are non-negative ints."""
    n, q = len(a), len(queries)
    block = max(1, int(n / max(1, q) ** 0.5))
    key = []
    for l, r in queries:
        b = l // block
        key.append(b * (n + 1) + (r if b % 2 == 0 else n - r))   # odd blocks go right to left
    order = sort_indices(key)                                    # piece: query ids in Mo order
    cnt = [0] * (max(a, default=0) + 1)
    ans = [0] * q
    cur_l, cur_r, distinct = 0, -1, 0
    for qid in order:
        l, r = queries[qid]
        while cur_l > l:                                         # grow first
            cur_l -= 1
            cnt[a[cur_l]] += 1
            distinct += cnt[a[cur_l]] == 1
        while cur_r < r:
            cur_r += 1
            cnt[a[cur_r]] += 1
            distinct += cnt[a[cur_r]] == 1
        while cur_l < l:                                         # then shrink
            cnt[a[cur_l]] -= 1
            distinct -= cnt[a[cur_l]] == 0
            cur_l += 1
        while cur_r > r:
            cnt[a[cur_r]] -= 1
            distinct -= cnt[a[cur_r]] == 0
            cur_r -= 1
        ans[qid] = distinct
    return ans

### moupd
--idea
Mo's algorithm with updates handles range queries on an array that also changes over time. Each query asks about a range as it was after the first `t` updates. The trick is to treat the number of applied updates `t` as a third coordinate next to the two ends `l` and `r`. Now the "window" has three moving parts: its left end, its right end, and the point in time, and you can move any of them one step at a time.
Moving the time forward by one means applying the next update; moving it back means undoing the last one. If the changed position lies inside the current window, the running answer must be adjusted too (remove the old value, add the new one). Sorting the queries by block of `l`, block of `r`, and then `t`, with blocks of size about `n^(2/3)`, keeps the total movement near `n^(5/3)`.
--build
1. Read the initial array `a`. Each update is `(pos, newValue)`, in the order it happens. Each query is `(l, r, t)`: the range `l..r` after the first `t` updates were applied.
2. Pre-compute `oldVal[k]` for each update `k`: simulate the updates once on a copy of the array and remember the value that update `k` overwrites. You need it to undo.
3. Choose `block = max(1, n^(2/3))`. A larger block than plain Mo's `sqrt(n)` is the balance for three moving parts.
4. Give each query the key `(l / block, r / block, t)` and sort the queries by it. (Equal blocks, then smaller `t` first.)
5. Keep the window `curL = 0, curR = -1`, the time `curT = 0`, a working copy `cur` of the array (starting as the initial array), the counts `cnt` and the running `distinct`.
6. For each query in order, first move `curL` and `curR` to `l` and `r` exactly as in Mo's algorithm: grow first, then shrink, using `add` and `remove` on `cur[...]`.
7. Then move the time to `t`. To apply update `k` (while `curT < t`): if `pos` is inside `[curL, curR]`, `remove(cur[pos])` and `add(newValue)`. Set `cur[pos] = newValue`. To undo update `k` (while `curT > t`, with `k = curT - 1`): the same, with `oldVal[k]` as the value to put back.
8. Store `ans[id] = distinct`.
9. All values (initial and updated) must fit the count array: compute `maxV` over the array and over the new values.
--think
- Signal: range queries with point changes in between, offline (all operations known), and an add and remove of one value are `O(1)`. Examples: distinct colours in a range with recolouring, number of values with frequency at least `k`.
- Decide whether a segment tree could do it. For decomposable answers (sum, maximum, gcd) a segment tree is simpler and faster: `O(log n)` per operation. Use Mo with updates when the answer needs the whole multiset of the range (distinct count, mode), which cannot be merged from two halves cheaply.
- Why the block size is `n^(2/3)`: with block `B`, the left and right ends move about `q * B` in total, and time moves about `(n / B)^2 * u` over all block pairs. Equating the two gives `B = n^(2/3)`, and the total is `O(n^(5/3))`.
- The time pointer only needs the update's old and new value: this is why you store `oldVal` ahead of time. Applying and undoing must be exact inverses.
- Pitfalls: forgetting that an update outside the window changes only `cur`, not the counts; applying time before the window moved (still correct if you use the window's current ends, but be consistent); a count array too small for the update values; and an update at the same position twice (each undo restores the right old value only if `oldVal` was computed in order).
--cost
Time `O(n^(5/3))` for `n` items and about `n` queries and updates. Space `O(n + q)`.

// updates[i] = {pos, newValue}; queries[j] = {l, r, t}: range l..r after the first t updates
static int[] moWithUpdates(int[] a, int[][] updates, int[][] queries) {
    int n = a.length, q = queries.length, u = updates.length;
    int[] cur = a.clone(), oldVal = new int[u];
    int maxV = 0;
    for (int x : a) maxV = Math.max(maxV, x);
    for (int k = 0; k < u; k++) {                          // old values, found by simulating once
        oldVal[k] = cur[updates[k][0]];
        cur[updates[k][0]] = updates[k][1];
        maxV = Math.max(maxV, updates[k][1]);
    }
    cur = a.clone();
    int block = Math.max(1, (int) Math.pow(n, 2.0 / 3));
    long[] key = new long[q];
    int blocks = n / block + 1;
    for (int i = 0; i < q; i++)
        key[i] = ((long) (queries[i][0] / block) * blocks + queries[i][1] / block) * (u + 1) + queries[i][2];
    Integer[] order = new Integer[q];
    for (int i = 0; i < q; i++) order[i] = i;
    Arrays.sort(order, (x, y) -> Long.compare(key[x], key[y]));
    cnt = new int[maxV + 1];
    distinct = 0;
    int[] ans = new int[q];
    int curL = 0, curR = -1, curT = 0;
    for (int id : order) {
        int l = queries[id][0], r = queries[id][1], t = queries[id][2];
        while (curL > l) addValue(cur[--curL]);
        while (curR < r) addValue(cur[++curR]);
        while (curL < l) removeValue(cur[curL++]);
        while (curR > r) removeValue(cur[curR--]);
        while (curT < t) {                                  // apply update curT
            int pos = updates[curT][0];
            if (curL <= pos && pos <= curR) { removeValue(cur[pos]); addValue(updates[curT][1]); }
            cur[pos] = updates[curT++][1];
        }
        while (curT > t) {                                  // undo update curT - 1
            int pos = updates[--curT][0];
            if (curL <= pos && pos <= curR) { removeValue(cur[pos]); addValue(oldVal[curT]); }
            cur[pos] = oldVal[curT];
        }
        ans[id] = distinct;
    }
    return ans;
}

def mo_with_updates(a, updates, queries):
    """updates[i] = (pos, new_value); queries[j] = (l, r, t): range l..r after the first t updates."""
    n, q, u = len(a), len(queries), len(updates)
    cur, old_val = list(a), [0] * u
    max_v = max(a, default=0)
    for k, (pos, val) in enumerate(updates):               # old values, found by simulating once
        old_val[k] = cur[pos]
        cur[pos] = val
        max_v = max(max_v, val)
    cur = list(a)
    block = max(1, int(n ** (2 / 3)))
    order = sorted(range(q), key=lambda i: (queries[i][0] // block, queries[i][1] // block, queries[i][2]))
    cnt = [0] * (max_v + 1)
    distinct = 0

    def add_value(v):
        nonlocal distinct
        cnt[v] += 1
        if cnt[v] == 1:
            distinct += 1

    def remove_value(v):
        nonlocal distinct
        cnt[v] -= 1
        if cnt[v] == 0:
            distinct -= 1

    ans = [0] * q
    cur_l, cur_r, cur_t = 0, -1, 0
    for qid in order:
        l, r, t = queries[qid]
        while cur_l > l:
            cur_l -= 1; add_value(cur[cur_l])
        while cur_r < r:
            cur_r += 1; add_value(cur[cur_r])
        while cur_l < l:
            remove_value(cur[cur_l]); cur_l += 1
        while cur_r > r:
            remove_value(cur[cur_r]); cur_r -= 1
        while cur_t < t:                                   # apply update cur_t
            pos, val = updates[cur_t]
            if cur_l <= pos <= cur_r:
                remove_value(cur[pos]); add_value(val)
            cur[pos] = val
            cur_t += 1
        while cur_t > t:                                   # undo update cur_t - 1
            cur_t -= 1
            pos = updates[cur_t][0]
            if cur_l <= pos <= cur_r:
                remove_value(cur[pos]); add_value(old_val[cur_t])
            cur[pos] = old_val[cur_t]
        ans[qid] = distinct
    return ans

### motree
--idea
Mo's algorithm on trees answers queries about the path between two nodes, such as "how many different colours appear on the path from `u` to `v`". The method works on arrays and ranges, so the plan is to turn each tree path into a range of an array. Walk the tree depth first and write down each node twice, once when you enter it and once when you leave it. That list is the Euler tour, of length `2n`.
The useful fact: if you take the part of that list between `u`'s exit and `v`'s entry (when neither is an ancestor of the other), a node that lies on the path appears exactly once, and every other node appears twice, either both times or not at all. So if "adding" a node means toggling it (on if off, off if on), the nodes that remain on are exactly the path nodes. After that it is the ordinary Mo's algorithm on the list, with toggle as the step.
--build
1. Build the adjacency lists and run the piece `dfs(v, parent)` from the root. It stores `tin[v]` when entering `v` and `tout[v]` when leaving, drawn from one counter `timer`, so all `2n` numbers are distinct.
2. Make `order` of length `2n` with `order[tin[v]] = order[tout[v]] = v`. This is the Euler tour.
3. Walk `order` with a stack to get `par[v]` and `depth[v]`: at the entry of `v`, its parent is the stack top; at the exit, pop.
4. Build the table `up[j][v]` (the `2^j`-th ancestor of `v`) from `par`, so that you can find the lowest common ancestor (`lca`) of two nodes in `O(log n)`.
5. Turn each query `(u, v)` into a range. Make sure `tin[u] <= tin[v]` (swap if needed). Let `w = lca(u, v)`. If `w == u` (u is an ancestor of v) use the range `[tin[u], tin[v]]` and no extra node. Otherwise use `[tout[u], tin[v]]` and one extra node `w`, which is on the path but not inside that range.
6. Sort the ranges for Mo's algorithm (block of the left end, then the right end, with the odd-even trick) over the `2n` positions.
7. Move the window with four loops as in plain Mo. To step onto or off a position, call `toggle(order[pos])`: if the node is on, switch it off and decrease its colour count (`distinct` drops when a count hits 0); otherwise switch it on and increase the count (`distinct` rises when a count becomes 1).
8. Answer for a query: `distinct`, plus one if there is an extra node `w` whose colour has count 0 in the window.
--think
- Signal: queries on the path between two nodes of a tree, where the answer depends on the set of values on the path and a single node can be added or removed in `O(1)`. Distinct colours on a path, how many nodes have a colour appearing an odd number of times.
- Decide whether simpler tools work. For path sums or maximums, use heavy-light decomposition or binary lifting with a sparse table. Mo on trees is for answers that need the whole multiset (distinct count, mode) which cannot be combined from pieces.
- The toggle trick is the heart. A node in the middle of the tour appears twice (once entering, once leaving) when its whole subtree lies inside the range, so toggling twice cancels it out. Only nodes whose entry or exit alone falls in the range stay on.
- The two cases for the range: if `u` is an ancestor of `v`, the whole path is inside `[tin[u], tin[v]]`, because nodes of `u`'s other branches are entered and left within the range and cancel. Otherwise the path from `u` up to the lca is covered by the exits after `tout[u]`, and the lca itself is never inside, hence the extra node.
- Related: Mo's algorithm on arrays, Mo with updates, Euler tour and lowest common ancestor, and heavy-light decomposition for decomposable queries.
- Pitfalls: not swapping so that `tin[u] <= tin[v]`, forgetting the extra lca node, a range over `n` positions instead of `2n`, and recursion depth for the `dfs` on a path-like tree (use an iterative version or a bigger stack for `n` of `10^5` or more).
--cost
Time `O((n + q) sqrt n + q log n)` for the window moves and the lowest common ancestors. Space `O(n log n)` for the ancestor table.

static List<List<Integer>> adj;
static int[] tin, tout;
static int timer;
// the piece dfs(v, p) numbers each node on entry (tin) and on exit (tout) from one counter

static int[] cnt;
static boolean[] on;
static int distinct;

static void toggle(int v, int[] color) {
    if (on[v]) { on[v] = false; if (--cnt[color[v]] == 0) distinct--; }
    else       { on[v] = true;  if (cnt[color[v]]++ == 0) distinct++; }
}

static int lca(int u, int v, int[][] up, int[] depth) {
    if (depth[u] < depth[v]) { int t = u; u = v; v = t; }
    for (int j = 0; j < up.length; j++)
        if ((depth[u] - depth[v] >> j & 1) == 1) u = up[j][u];     // lift u to the depth of v
    if (u == v) return u;
    for (int j = up.length - 1; j >= 0; j--)
        if (up[j][u] != up[j][v]) { u = up[j][u]; v = up[j][v]; }
    return up[0][u];
}

// queries[i] = {u, v}; result[i] = distinct colours on the path u..v; colours are 0, 1, 2, ...
static int[] distinctOnPaths(int n, int[][] edges, int[] color, int[][] queries) {
    adj = new ArrayList<>();
    for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
    for (int[] e : edges) { adj.get(e[0]).add(e[1]); adj.get(e[1]).add(e[0]); }
    tin = new int[n]; tout = new int[n]; timer = 0;
    dfs(0, -1);                                                    // piece: entry and exit times
    int[] order = new int[2 * n], par = new int[n], depth = new int[n];
    for (int v = 0; v < n; v++) { order[tin[v]] = v; order[tout[v]] = v; }
    Deque<Integer> stack = new ArrayDeque<>();
    for (int i = 0; i < 2 * n; i++) {                              // parents and depths from the tour
        int v = order[i];
        if (tin[v] == i) { par[v] = stack.isEmpty() ? v : stack.peek(); depth[v] = stack.size(); stack.push(v); }
        else stack.pop();
    }
    int log = 1;
    while ((1 << log) < n) log++;
    int[][] up = new int[log][];
    up[0] = par;
    for (int j = 1; j < log; j++) {
        up[j] = new int[n];
        for (int v = 0; v < n; v++) up[j][v] = up[j - 1][up[j - 1][v]];
    }
    int q = queries.length, m = 2 * n;
    int[] ql = new int[q], qr = new int[q], extra = new int[q];
    for (int i = 0; i < q; i++) {                                  // path -> range (+ maybe the lca)
        int u = queries[i][0], v = queries[i][1];
        if (tin[u] > tin[v]) { int t = u; u = v; v = t; }
        int w = lca(u, v, up, depth);
        if (w == u) { ql[i] = tin[u]; qr[i] = tin[v]; extra[i] = -1; }
        else        { ql[i] = tout[u]; qr[i] = tin[v]; extra[i] = w; }
    }
    int block = Math.max(1, (int) (m / Math.sqrt(Math.max(1, q))));
    long[] key = new long[q];
    for (int i = 0; i < q; i++) {
        int b = ql[i] / block;
        key[i] = (long) b * (m + 1) + (b % 2 == 0 ? qr[i] : m - qr[i]);
    }
    Integer[] ids = new Integer[q];
    for (int i = 0; i < q; i++) ids[i] = i;
    Arrays.sort(ids, (x, y) -> Long.compare(key[x], key[y]));
    int maxC = 0;
    for (int c : color) maxC = Math.max(maxC, c);
    cnt = new int[maxC + 1]; on = new boolean[n]; distinct = 0;
    int[] ans = new int[q];
    int curL = 0, curR = -1;
    for (int id : ids) {
        while (curL > ql[id]) toggle(order[--curL], color);
        while (curR < qr[id]) toggle(order[++curR], color);
        while (curL < ql[id]) toggle(order[curL++], color);
        while (curR > qr[id]) toggle(order[curR--], color);
        ans[id] = distinct + (extra[id] >= 0 && cnt[color[extra[id]]] == 0 ? 1 : 0);
    }
    return ans;
}

def lca(u, v, up, depth):
    if depth[u] < depth[v]:
        u, v = v, u
    diff = depth[u] - depth[v]
    for j in range(len(up)):
        if diff >> j & 1:
            u = up[j][u]                                          # lift u to the depth of v
    if u == v:
        return u
    for j in range(len(up) - 1, -1, -1):
        if up[j][u] != up[j][v]:
            u, v = up[j][u], up[j][v]
    return up[0][u]

def distinct_on_paths(n, edges, color, queries):
    """queries is a list of (u, v); returns the distinct colours on each path; colours are 0, 1, 2, ..."""
    global adj, tin, tout, timer
    adj = [[] for _ in range(n)]
    for a, b in edges:
        adj[a].append(b)
        adj[b].append(a)
    tin, tout, timer = [0] * n, [0] * n, 0
    dfs(0, -1)                                                    # piece: entry and exit times
    order, par, depth, stack = [0] * (2 * n), [0] * n, [0] * n, []
    for v in range(n):
        order[tin[v]] = order[tout[v]] = v
    for i, v in enumerate(order):                                 # parents and depths from the tour
        if tin[v] == i:
            par[v] = stack[-1] if stack else v
            depth[v] = len(stack)
            stack.append(v)
        else:
            stack.pop()
    up = [par]
    while (1 << len(up)) < n:
        up.append([up[-1][up[-1][v]] for v in range(n)])
    m, rng = 2 * n, []
    for u, v in queries:                                          # path -> range (+ maybe the lca)
        if tin[u] > tin[v]:
            u, v = v, u
        w = lca(u, v, up, depth)
        rng.append((tin[u], tin[v], -1) if w == u else (tout[u], tin[v], w))
    block = max(1, int(m / max(1, len(queries)) ** 0.5))
    ids = sorted(range(len(queries)), key=lambda i: (rng[i][0] // block,
                 rng[i][1] if rng[i][0] // block % 2 == 0 else -rng[i][1]))
    cnt, on, distinct = [0] * (max(color) + 1), [False] * n, 0
    ans = [0] * len(queries)
    cur_l, cur_r = 0, -1

    def toggle(v):
        nonlocal distinct
        if on[v]:
            on[v] = False
            cnt[color[v]] -= 1
            distinct -= cnt[color[v]] == 0
        else:
            on[v] = True
            cnt[color[v]] += 1
            distinct += cnt[color[v]] == 1

    for i in ids:
        l, r, w = rng[i]
        while cur_l > l:
            cur_l -= 1; toggle(order[cur_l])
        while cur_r < r:
            cur_r += 1; toggle(order[cur_r])
        while cur_l < l:
            toggle(order[cur_l]); cur_l += 1
        while cur_r > r:
            toggle(order[cur_r]); cur_r -= 1
        ans[i] = distinct + (1 if w >= 0 and cnt[color[w]] == 0 else 0)
    return ans

### cdq
--idea
CDQ divide and conquer (named after a Chinese competitive programmer) counts relations between items that depend on several conditions at once, by splitting the items in half by their position (often time), solving each half, and then counting the pairs that straddle the middle. The key is that inside one level, the first condition (earlier index) is already guaranteed by the split, so you only need to handle the remaining conditions for pairs where the left item comes from the left half and the right item from the right half.
The example here counts pairs `i < j` with `a[i] < a[j]` and `b[i] < b[j]`: three conditions (index, `a`, `b`). After the split the index condition holds for every left-right pair. Sort both halves by `a`, sweep through them with two pointers adding the left items to a Fenwick tree indexed by `b`, and for each right item ask how many left items have a smaller `b`. This is merge sort with a counting step, and it is the 3D version of counting inversions.
--build
1. Inputs `a` and `b` are lists of ranks in `0..n-1` (compress them first). Pack each item as one integer `key = a * n + b`, so sorting the keys sorts by `a`, then `b`, and `a = key / n`, `b = key % n` can be read back. This needs `n * n` to fit an `int` (about `n <= 46000`).
2. `solve(lo, hi)` handles items `lo..hi-1` and returns their keys sorted. If there is one item, return it.
3. Split at `mid = (lo + hi) / 2`. Get `left = solve(lo, mid)` and `right = solve(mid, hi)`. Each is sorted by key.
4. Count the crossing pairs. Walk through `right` in increasing key order with a pointer `i` into `left`. Before handling a right item `y`, move `i` forward while `left[i]` has a smaller `a` than `y`, adding that item's `b` to the Fenwick tree (`bitAdd`).
5. The number of left items with smaller `a` and smaller `b` than `y` is `bitSum(b(y) - 1)`. Add it to `total`.
6. Undo: subtract every `b` you added from the tree (the tree must be empty for the next call).
7. Merge `left` and `right` into one sorted list with the piece `merge` and return it, so the parent level can count with it.
8. The answer is `total` after `solve(0, n)`.
--think
- Signal: counting or optimising over pairs `(i, j)` with two or more ordering conditions: "`i < j`, `a[i] < a[j]`, `b[i] < b[j]`", longest chain in 3D, dynamic programming where `dp[j]` depends on earlier `i` with conditions on two other values, and offline problems with time, position and value.
- Decide which condition to make the "split" (usually the index or the time). The split makes that condition free. Then sort by the second, and use a data structure (Fenwick tree) for the third.
- The invariant: after `solve(lo, hi)` the returned list is sorted, and `total` has counted every pair inside `lo..hi-1`. The parent only needs the cross pairs. Each pair is counted exactly once, at the level where the two items first land in different halves.
- For dynamic programming, CDQ gives the order: solve the left half completely, use it to update the right half's values, then solve the right half. It handles dependencies that depend on earlier items with extra conditions.
- Related: counting inversions (divide and conquer with one condition fewer), offline Fenwick sweeps (two conditions), and k-d trees or persistent trees (online alternatives).
- Pitfalls: not clearing the Fenwick tree after a level (answers leak into other calls), equal values (the code uses strict `<` on both `a` and `b`; change the comparisons for `<=`), the packed key overflowing for large `n` (use `long` and your own merge then), and forgetting to merge so the next level sees sorted halves.
--cost
Time `O(n log^2 n)`: `log n` levels, each with a merge and Fenwick work of `O(n log n)`. Space `O(n)`.
--java
static long total;
static int[] bit;
static int size;                       // n, the number of items

static void bitAdd(int i, int v) { for (i++; i <= size; i += i & -i) bit[i] += v; }

static int bitSum(int i) {             // sum over positions 0..i (0 if i < 0)
    int s = 0;
    for (i++; i > 0; i -= i & -i) s += bit[i];
    return s;
}

// keys[i] = a[i] * n + b[i]; returns the keys of lo..hi-1 sorted and adds the pairs to total
static int[] solve(int[] keys, int lo, int hi) {
    if (hi - lo == 1) return new int[]{keys[lo]};
    int mid = (lo + hi) >>> 1;
    int[] left = solve(keys, lo, mid), right = solve(keys, mid, hi);
    int i = 0;
    for (int y : right) {                                   // right items in increasing key order
        while (i < left.length && left[i] / size < y / size)
            bitAdd(left[i++] % size, 1);                    // left items with a smaller a
        total += bitSum(y % size - 1);                      // ...and a smaller b
    }
    for (int k = 0; k < i; k++) bitAdd(left[k] % size, -1); // clear the tree
    return merge(left, right);                              // piece: keep the halves sorted
}

        i += 1
        while i <= n:
            bit[i] += v
            i += i & -i

            i -= i & -i

### smalllarge
--idea
Small to large merging is a way to combine many sets cheaply. When you must merge two sets, copy the elements of the smaller into the larger, never the other way around. Each time an element is copied, it ends up in a set at least twice as big as before. A set can only double about `log n` times before it holds everything, so each element is copied at most `log n` times, and the total work over all merges is `O(n log n)`, not `O(n^2)`.
Think of merging crowds of people into one hall: always send the smaller crowd to join the bigger one. A person only has to walk when their crowd is at most half the size of the new one, so nobody walks more than `log n` times. The classic use is on a tree: the answer for a node depends on the set of values in its subtree, so you merge each child's set into the parent's.
--build
1. Root the tree and get an order in which every node comes after its parent (a breadth first order from the root). Reading that order backwards visits every node after all of its descendants.
2. Give each node its own map `sets[v]` from value (colour) to how many times it appears. At the start it holds only the node's own colour: `{color[v]: 1}`.
3. Process nodes in reverse order. When it is `v`'s turn, all its children are already merged into `sets[v]`, so the answer is `ans[v] = size of sets[v]` (the number of distinct colours in the subtree).
4. Merge `sets[v]` into its parent `p`. First swap the two references if `sets[v]` is bigger than `sets[p]`, so that `sets[p]` is the larger one. The swap moves only a pointer, no elements.
5. Then go through the smaller map and for each `(colour, count)` set `big[colour] = getOrDefault(big, colour, 0) + count`, with the piece `getOrDefault`.
6. After the merge `sets[p]` holds the combined map. The smaller map is no longer needed; drop it.
7. Why `O(n log n)`: only elements of the smaller set are copied, and each copy at least doubles the size of the set that element lives in.
--think
- Signal: a tree (or a sequence of merges) where each node needs a statistic of the multiset of values in its subtree: number of distinct values, most frequent value, a sum over colours. Also "union of sets over a sequence of merges" such as merging groups in a game.
- Decide whether the statistic can be kept as you merge. Distinct count: the size of the map. Most frequent value: also keep the current best and update it as counts rise. If you need per-colour counts to be undone (removal), the sack technique ("DSU on tree") is an alternative that avoids maps.
- The rule is about always moving the smaller into the larger, and swapping references (not copying) to make the larger one the base. Forgetting the swap makes a chain tree cost `O(n^2)`.
- Related: Mo's algorithm on trees (offline and slower), Euler tour with a segment tree, merging segment trees (which also has an amortised `O(n log n)` argument), and union-find with sizes (the same "attach smaller to larger" idea).
- Pitfalls: copying the larger set into the smaller one, forgetting to process a node's own colour at the start, using recursion on a deep tree (use the order trick above), and keeping counts only as a set (you cannot then remove a colour correctly).
--cost
Time `O(n log n)` map operations (each `O(1)` expected with a hash map, `O(log n)` with an ordered map). Space `O(n)`.
--java
// colour counts for the subtree of each node; the tree is rooted at node 0
static int[] distinctInSubtrees(int n, int[][] edges, int[] color) {
    List<List<Integer>> adj = new ArrayList<>();
    for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
    for (int[] e : edges) { adj.get(e[0]).add(e[1]); adj.get(e[1]).add(e[0]); }
    int[] parent = new int[n], order = new int[n];
    Arrays.fill(parent, -1);
    int head = 0, tail = 0;
    order[tail++] = 0;
    while (head < tail) {                                    // breadth first order: parents come first
        int v = order[head++];
        for (int w : adj.get(v)) if (w != parent[v]) { parent[w] = v; order[tail++] = w; }
    }
    List<Map<Integer, Integer>> sets = new ArrayList<>();
    for (int v = 0; v < n; v++) {
        Map<Integer, Integer> m = new HashMap<>();
        m.put(color[v], 1);                                  // the node's own colour
        sets.add(m);
    }
    int[] ans = new int[n];
    for (int i = n - 1; i >= 0; i--) {                       // descendants are processed before the node
        int v = order[i], p = parent[v];
        ans[v] = sets.get(v).size();
        if (p < 0) continue;
        if (sets.get(v).size() > sets.get(p).size()) {       // make sets[p] the larger one: swap references
            Map<Integer, Integer> t = sets.get(v); sets.set(v, sets.get(p)); sets.set(p, t);
        }
        Map<Integer, Integer> big = sets.get(p);
        for (Map.Entry<Integer, Integer> e : sets.get(v).entrySet())       // copy only the smaller one
            big.put(e.getKey(), getOrDefault(big, e.getKey(), 0) + e.getValue());   // piece
    }
    return ans;
}

def distinct_in_subtrees(n, edges, color):
    """Number of distinct colours in the subtree of each node; the tree is rooted at node 0."""
    adj = [[] for _ in range(n)]
    for a, b in edges:
        adj[a].append(b)
        adj[b].append(a)
    parent, order = [-1] * n, [0]
    for v in order:                                          # breadth first order: parents come first
        for w in adj[v]:
            if w != parent[v]:
                parent[w] = v
                order.append(w)
    sets = [{color[v]: 1} for v in range(n)]                 # each node starts with its own colour
    ans = [0] * n
    for v in reversed(order):                                # descendants are processed before the node
        p = parent[v]
        ans[v] = len(sets[v])
        if p < 0:
            continue
        if len(sets[v]) > len(sets[p]):                      # make sets[p] the larger one: swap references
            sets[v], sets[p] = sets[p], sets[v]
        big = sets[p]
        for c, k in sets[v].items():                         # copy only the smaller one
            big[c] = get_or_default(big, c) + k              # piece
    return ans

// colour counts for the subtree of each node; the tree is rooted at node 0
vector<int> distinctInSubtrees(int n, const vector<pair<int, int>>& edges, const vector<int>& color) {
    vector<vector<int>> adj(n);
    for (auto& e : edges) { adj[e.first].push_back(e.second); adj[e.second].push_back(e.first); }
    vector<int> parent(n, -1), order = {0};

        int v = order[i];
        for (int w : adj[v]) if (w != parent[v]) { parent[w] = v; order.push_back(w); }
    }
    vector<map<int, int>> sets(n);
    for (int v = 0; v < n; v++) sets[v][color[v]] = 1;       // the node's own colour
    vector<int> ans(n);
    for (int i = n - 1; i >= 0; i--) {                       // descendants are processed before the node
        int v = order[i], p = parent[v];
        ans[v] = sets[v].size();
        if (p < 0) continue;
        if (sets[v].size() > sets[p].size()) swap(sets[v], sets[p]);   // swapping maps moves pointers only
        for (auto& e : sets[v])                              // copy only the smaller one
            sets[p][e.first] = getOrDefault(sets[p], e.first, 0) + e.second;   // piece
    }
    return ans;
}

### random
--idea
Randomization means letting chance make some of the choices in your algorithm so that no fixed input can reliably make it slow or wrong. If a quick-sort always takes the first item as the pivot, an already sorted list makes it take quadratic time. If it takes a random item, no input is bad: the expected time is `n log n` for every input, because a random pivot is usually near the middle.
There are two flavours. Las Vegas algorithms always give the right answer, and only the running time is random (random pivots, random shuffles). Monte Carlo algorithms run fast but may be wrong with a small probability that you can shrink by repeating (checking a matrix product with random vectors, testing primes). The idea is to trade a certainty you do not need for simplicity or speed.
--build
1. Find the step where a bad input could hurt (choosing a pivot, ordering the items, picking a hash).
2. Replace the fixed choice by a random one with the piece `randInt(lo, hi)` (inclusive), which returns a random whole number in the range.
3. Example one, shuffle: for `i` from `0` to `n - 2` swap `a[i]` with `a[randInt(i, n - 1)]`. Every ordering is equally likely (the Fisher-Yates shuffle).
4. Example two, quickselect (find the `k`-th smallest without sorting): pick a random pivot `p` with `randInt(lo, hi)`. Split the range into items less than `p`, equal to `p`, greater than `p` (three groups).
5. If `k` lies in the first group, keep only that group; if in the last, keep only that group; otherwise `p` is the answer. Repeat on the smaller range.
6. Expected work is `n + n/2 + n/4 + ... = 2n`, because a random pivot cuts the range by a constant factor on average.
7. Always test with a brute force: a random algorithm that fails rarely is hard to debug, so compare with a slow exact answer on many small inputs.
--think
- Signal: an algorithm whose worst case comes from adversarial input (sorted data, anti-hash tests, anti-quicksort tests) while the average case is fine; problems where you need a "typical" element; or a check that can be done on a random sample instead of everything.
- Decide which kind you need. If a wrong answer is never acceptable, use a Las Vegas method (the answer is exact, only the time varies). If a tiny error probability is fine, a Monte Carlo method can be far simpler. Repeating `k` times a test with error at most `1/2` gives error at most `2^-k`.
- Where it helps: quicksort and quickselect pivots, shuffling input before a method that dislikes order, randomised hashing (random base and modulus), random sampling, treaps (random priorities keep a tree balanced), and probabilistic primality tests.
- Seeding: use a time-based seed in contests with hacks (a fixed seed can be attacked); use a fixed seed when you want a reproducible bug.
- Related: local search and hill climbing (random restarts), approximation algorithms, hashing.
- Pitfalls: using the wrong range for `randInt` (it is inclusive on both ends), biased shuffles (swapping with `randInt(0, n - 1)` every time is not uniform), a poor generator (`rand() % n` in C is weak), and assuming a random algorithm is reproducible when it is not.
--cost
Quickselect is `O(n)` expected, `O(n^2)` worst case with astronomically small probability. A shuffle is `O(n)`.
--java
// uniformly random order, in place (Fisher-Yates)
static void shuffle(int[] a) {
    for (int i = 0; i < a.length - 1; i++) {
        int j = randInt(i, a.length - 1);          // piece: pick from the not-yet-fixed part
        int t = a[i]; a[i] = a[j]; a[j] = t;
    }
}

// the k-th smallest value (k counts from 0), without sorting
static int kthSmallest(int[] a, int k) {
    int[] b = a.clone();
    int lo = 0, hi = b.length - 1;
    while (true) {
        int pivot = b[randInt(lo, hi)];            // piece: a random pivot
        int lt = lo, i = lo, gt = hi;              // three groups: < pivot, == pivot, > pivot
        while (i <= gt) {
            if (b[i] < pivot) { int t = b[lt]; b[lt++] = b[i]; b[i++] = t; }
            else if (b[i] > pivot) { int t = b[gt]; b[gt--] = b[i]; b[i] = t; }
            else i++;
        }
        if (k < lt) hi = lt - 1;                   // the answer is among the smaller ones
        else if (k > gt) lo = gt + 1;              // ... among the larger ones
        else return pivot;                         // ... or equals the pivot
    }
}

### simulate
--idea
Simulation means doing exactly what the statement describes, step by step, and reading off the result. There is no clever formula: you model the state (a grid, a queue, a list), apply the rules one round at a time, and stop when the statement says to. It is the right answer when the number of steps fits the time limit, and it is also the reference solution you compare faster ideas against.
The skill is in being exact. Decide what the state is, what one step does, in what order the parts of a step happen, and when to stop. In a grid game where all cells change at the same moment (Conway's Game of Life), you must read every cell from the old grid and write into a new one; writing into the same grid while reading breaks the rule.
--build
1. List the state: for Game of Life, a grid of cells, each alive (1) or dead (0), stored in a flat array of `rows * cols` items.
2. Write one step as a function from the old state to a new state. Never change the old state while reading it.
3. To turn a row and column into a position of the flat array use the piece `idx(r, c, cols)`. To test whether a neighbour exists use `inBounds(rr, cc, rows, cols)`.
4. For the neighbours of a cell, take the 8 direction pairs from the piece `dirs(true)` (`dirs(false)` gives the four straight ones) and add each to `(r, c)`.
5. Count the alive neighbours. Rule: a cell is alive next round if it has exactly 3 alive neighbours, or if it is alive now and has exactly 2.
6. Repeat the step as many times as the statement says. If the number of rounds is huge, look for a cycle in the states (the state repeats, so you can skip ahead) before simulating everything.
7. Second example, `josephus`: `n` people stand in a circle and every `k`-th person is removed until one is left. Keep a list and a position `pos`; move `pos = (pos + k - 1) % size`, remove that person, and repeat. The survivor is the last one.
--think
- Signal: the statement describes a process ("each second", "every round", "a robot follows these commands"), and the limits allow the number of steps (for example `n * steps <= 10^8`). If a very long process has a repeating pattern, simulation plus cycle detection is the plan.
- Decide the state representation first. A flat array with `idx` is faster and simpler than nested lists. Decide whether updates are simultaneous (copy into a new array) or one after another (change in place).
- Read the statement for the order of events inside one step, the tie-breaking rules, and what happens at the edges (does the grid wrap around or stop?). Most wrong answers on simulation problems are a misread rule, not an algorithmic mistake.
- If the simulation is too slow, find what repeats (a cycle: see fast and slow pointers) or what can be skipped (events in a priority queue instead of ticking every second), or find the closed form (the Josephus problem has an `O(n)` recurrence).
- As a tool: write the simulation first as the slow correct version, and use it to test every clever solution.
- Pitfalls: updating in place when the rule is simultaneous, off-by-one in the number of rounds, counting a cell as its own neighbour, and forgetting the boundary check.
--cost
Time is steps times the work per step: Game of Life costs `O(rows * cols)` per round; the Josephus list version `O(n^2)` because removing from a list is linear.
--java
// one round of Game of Life on a rows x cols grid stored in a flat array (1 = alive)
static int[] lifeStep(int[] cell, int rows, int cols) {
    int[] next = new int[cell.length];                       // write into a new grid, read from the old one
    int[][] steps = dirs(true);                              // piece: the 8 neighbour directions
    for (int r = 0; r < rows; r++)
        for (int c = 0; c < cols; c++) {
            int alive = 0;
            for (int[] d : steps) {
                int rr = r + d[0], cc = c + d[1];
                if (inBounds(rr, cc, rows, cols))            // piece: stay on the board
                    alive += cell[idx(rr, cc, cols)];        // piece: flat position
            }
            int me = cell[idx(r, c, cols)];
            next[idx(r, c, cols)] = (alive == 3 || (me == 1 && alive == 2)) ? 1 : 0;
        }
    return next;
}

// n people in a circle, every k-th is removed; returns the survivor's number (1 to n)
static int josephus(int n, int k) {
    List<Integer> people = new ArrayList<>();
    for (int i = 1; i <= n; i++) people.add(i);
    int pos = 0;
    while (people.size() > 1) {
        pos = (pos + k - 1) % people.size();                 // count k people, wrapping around
        people.remove(pos);                                  // that person leaves; pos now points to the next
    }
    return people.get(0);
}

    for r in range(rows):
        for c in range(cols):
            alive = 0
            for dr, dc in steps:
                rr, cc = r + dr, c + dc
                if in_bounds(rr, cc, rows, cols):            # piece: stay on the board
                    alive += cell[idx(rr, cc, cols)]         # piece: flat position
            me = cell[idx(r, c, cols)]
            nxt[idx(r, c, cols)] = 1 if alive == 3 or (me == 1 and alive == 2) else 0
    return nxt

### constructive
--idea
A constructive problem asks you to build an object that satisfies some rules: an arrangement, a string, a grid, a list of moves. You are not asked for the best one or how many there are, just to produce one that works (or to say that none exists). The art is to find a pattern that always works, by looking at small cases, and then to prove that the pattern really does satisfy every rule.
Think of a tailor who does not try every cut of cloth but follows a method that always fits. For the permutation of `1..n` in which the gaps between neighbours are all different, the method is to alternate between the smallest and the largest unused number: `1, n, 2, n - 1, ...`. The gaps are then `n - 1, n - 2, n - 3, ...`, each different, so the rule holds for every `n`.
--build
1. Read the rules carefully and write them as a checkable test (a function that says "valid or not"). You will need it to try small cases.
2. Solve tiny cases by hand or by brute force: `n = 1, 2, 3, 4, 5`. Print the valid answers and look for a shape.
3. Guess a pattern, such as alternating ends, pairing items, filling in layers, or building from the answer for `n - 1`. State it as a rule that needs no search.
4. Write the rule as code. For the zigzag permutation: keep `lo = 1` and `hi = n`; at even positions emit `lo` and increase it, at odd positions emit `hi` and decrease it (`zigzag`).
5. Prove the rule always works. Here: the `i`-th gap has size `n - i`, so all the gaps are different. Then run the validity test from step 1 on many `n` to catch what the proof missed.
6. Decide when the answer does not exist. Find a bound that shows it is impossible (a count, a sum, parity) and return "impossible" in those cases. Example (`distinctWithSum`): `n` distinct positive numbers have a sum of at least `1 + 2 + ... + n`, so a smaller target is impossible. Otherwise use `1, 2, ..., n - 1` and let the last number take the rest of the sum.
7. Check the extreme cases: `n = 1`, the smallest and the largest allowed inputs.
--think
- Signal: "construct", "find any", "output any valid arrangement", "print `-1` if impossible". There are usually many valid answers, so the checker accepts any one, and the limits are large (so no search).
- First step: try the small cases and look for the pattern. Second: ask what natural bound or invariant would make the task impossible, because that tells you which inputs to reject and which are always possible.
- Standard constructions: alternate between ends (zigzag), sort then pair first with last, build by induction (an answer for `n` from one for `n - 1`), layer by layer, use a base case and extend, or construct from the extremes (put the largest where it is most constrained). Greedy construction (fix the most constrained thing first) is a common first try.
- To prove it works: show the rule satisfies every constraint for all `n` (direct check, or by induction), and that every input not rejected is handled. A pattern that works for `n <= 10` but was never proved is a typical trap.
- If you cannot find a pattern, search for a small counterexample by brute force (backtracking). That often shows why the problem is impossible or reveals the missing case.
- Pitfalls: handling only even `n` or only odd `n`, off-by-one at the ends of the pattern, not meeting a hidden constraint (values must be at most some limit), and printing a non-valid answer for a case you never tested.
--cost
Usually `O(n)` to write out the answer, with no search at all.
--java
// permutation of 1..n whose neighbouring differences |p[i] - p[i+1]| are all different
static int[] zigzag(int n) {
    int[] p = new int[n];
    int lo = 1, hi = n;
    for (int i = 0; i < n; i++)
        p[i] = (i % 2 == 0) ? lo++ : hi--;      // alternate: smallest left, largest left
    return p;                                   // the gaps are n-1, n-2, ..., 1
}

// n distinct positive integers with sum exactly s, or null if impossible
static int[] distinctWithSum(int n, long s) {
    if (s < (long) n * (n + 1) / 2) return null;   // even 1..n is too big: impossible
    int[] a = new int[n];
    long used = 0;
    for (int i = 0; i < n - 1; i++) { a[i] = i + 1; used += i + 1; }   // 1, 2, ..., n-1
    a[n - 1] = (int) (s - used);                // the rest, at least n, so still distinct
    return a;
}

        return None

    return a

### invariants
--idea
An invariant is a quantity that never changes when you apply the allowed moves. If a puzzle lets you change things in complicated ways but some number stays the same, then anything that would need that number to change is impossible, and the final result may be predicted without playing the game at all. A monovariant is a weaker cousin: a quantity that only ever goes one way (always grows, or always shrinks). It proves the process must end, and gives a bound on how many steps it can take.
Example: a board holds numbers. A move erases two numbers `x` and `y` and writes `x + y - 1`. The sum changes, and the count changes. But the sum minus the count does not: the sum drops by 1 and the count drops by 1. So `sum - count` is an invariant. When one number `f` remains, `f - 1` must equal the starting `sum - count`, so `f = sum - count + 1` whatever order the moves are made in.
--build
1. Write down the state and the allowed move precisely. Here the state is the list of numbers and a move merges two of them.
2. Look for a quantity that depends on the state: sum, count, parity (odd or even), a colouring count, a product, a remainder. Compute how a single move changes each of them.
3. A quantity whose change is zero is an invariant. A quantity whose changes are always positive (or always negative) is a monovariant. Sometimes you must combine two quantities so the changes cancel, as `sum - count` does.
4. Use the invariant. To predict the result: compute it at the start and express the end state through it (`finalByInvariant`: `sum - count + 1`). To prove impossibility: show the target state has a different value of the invariant than the start.
5. Use the monovariant. To prove a process stops: show the quantity is a whole number that is bounded and always changes in one direction.
6. Check the claim by brute force on small cases: simulate with different move orders (`finalBySimulation`) and confirm the result is the same every time.
--think
- Signal: a game or process with a long list of moves where the question is "can we reach this state?", "what is the final value?", or "does it always end?". Phrases like "no matter what order" or "prove it is impossible" are the strongest hints. Also board tilings with removed squares and token-sliding games.
- Decide what to measure. Try sum, count, parity of the count, sum modulo `m` for a small `m`, colouring a board with two colours (a domino covers one of each), and the number of inversions of a permutation (a swap of neighbours changes it by one).
- To prove something is impossible, the invariant must differ between the start and the target. To prove it is possible, an invariant is not enough: you must also build the sequence of moves (that is a constructive argument).
- Monovariant proofs are the standard way to show termination: "this value is a non-negative integer that drops every step", so there can be only finitely many steps. Choosing the right quantity is the whole difficulty.
- Related: parity arguments (the most common invariant), constructive thinking (to show a target is reachable), and game theory (positions with an invariant such as the XOR in Nim).
- Pitfalls: finding an invariant that is true but too weak to separate start and target, assuming "the invariant matches" means the target is reachable (it only means it is not ruled out), and mistakes in computing how a move changes the quantity.
--cost
Using the invariant is `O(n)` (one pass to sum). Simulating the moves is `O(n^2)` for the list version below.
--java
// the last number left, found in one pass: sum - count is unchanged by a move
static long finalByInvariant(long[] nums) {
    long sum = 0;
    for (long x : nums) sum += x;
    return sum - nums.length + 1;               // f - 1 = sum - count
}

// the same result by really playing the moves (first two numbers, result goes to the back)
static long finalBySimulation(long[] nums) {
    Deque<Long> q = new ArrayDeque<>();
    for (long x : nums) q.addLast(x);
    while (q.size() > 1) {
        long x = q.pollFirst(), y = q.pollFirst();
        q.addLast(x + y - 1);                   // one move
    }
    return q.peekFirst();
}

### pigeonhole
--idea
The pigeonhole principle says: if you put more than `k` items into `k` boxes, some box holds at least two items. It sounds obvious, and its power is in choosing the boxes cleverly so that "two in the same box" means something you want. It proves that something must exist, and often tells you where to look for it.
Example: take any `n` whole numbers. Some run of consecutive ones adds up to a multiple of `n`. Why: look at the `n + 1` running totals (including the empty total 0), each taken modulo `n`. There are only `n` possible remainders, so two running totals have the same remainder. The numbers between those two positions add up to the difference of the totals, which is a multiple of `n`.
--build
1. Say what the "items" are and what the "boxes" are. Items are the objects you can count; boxes are the categories they fall into (remainders, ranges, colours).
2. Count them. If items outnumber boxes, two items share a box.
3. Choose the boxes so that sharing a box gives the structure you need. For subarray sums, items are the `n + 1` prefix sums and boxes are the `n` remainders; two items in the same box means the sum between them is divisible by `n`.
4. To find the pair in code, remember the first position of each box: `firstSeen[remainder]`. When a new item lands in a box already seen, you have the pair (`subarrayDivisibleByN`). Start with `firstSeen[0] = -1`, which stands for the empty prefix.
5. Use `((sum % n) + n) % n` so negative numbers give a valid box number.
6. A second example (`findDuplicate`): `n + 1` numbers in `1..n` have a repeat. Mark each number in a `seen` array; the first number already marked is a duplicate.
7. The principle gives only existence. The code finds the pair by scanning, once, in `O(n)`.
--think
- Signal: "prove that there exist two ...", "show that some ... must", "among any `n + 1` numbers", "at least one is always ...", or a task whose answer is guaranteed to exist ("it can be shown that a solution always exists").
- Decide the boxes. Common choices: remainders modulo `m`, which half of an interval a point lies in, distance classes, bit patterns, and groups of equal prefix values.
- The stronger form: if `n` items go into `k` boxes, some box holds at least `ceil(n / k)` items. Use it for "at least `m` items of the same colour".
- To use it constructively, combine with a scan that stores the first occurrence of each box, as above. For existence only, no code is needed, but a solution can still ask you to print the pair.
- Related: prefix sums with a hash map (the same remainder trick), the pigeonhole bound in hashing (collisions are unavoidable), and parity arguments (two boxes: even and odd).
- Pitfalls: forgetting the empty prefix (so only `n` items, no guarantee), the wrong box count (remainders `0..n - 1` are `n` boxes), negative remainders, and using the principle where items do not outnumber boxes (then no guarantee).
--cost
`O(n)` time and `O(n)` space for each scan.
--java
// indices {l, r} (both included) so that a[l..r] sums to a multiple of n; always exists
static int[] subarrayDivisibleByN(int[] a) {
    int n = a.length;
    if (n == 0) return null;
    int[] firstSeen = new int[n];                    // remainder -> index where that prefix ended
    Arrays.fill(firstSeen, -2);                      // -2 means "not seen"
    firstSeen[0] = -1;                               // the empty prefix, before index 0
    long sum = 0;
    for (int i = 0; i < n; i++) {
        sum += a[i];
        int rem = (int) (((sum % n) + n) % n);       // the box of this prefix
        if (firstSeen[rem] != -2) return new int[]{firstSeen[rem] + 1, i};   // two in one box
        firstSeen[rem] = i;
    }
    return null;                                     // cannot happen: n + 1 prefixes, n boxes
}

// a number that repeats in an array of n + 1 values from 1..n
static int findDuplicate(int[] a) {
    boolean[] seen = new boolean[a.length];
    for (int x : a) {
        if (seen[x - 1]) return x;               // this box is already taken
        seen[x - 1] = true;
    }
    return -1;                                       // cannot happen
}

def subarray_divisible_by_n(a):
    """Indices (l, r), both included, so that a[l..r] sums to a multiple of n; always exists."""
    n = len(a)
    if n == 0:
        return None
    first_seen = {0: -1}                             # remainder -> index where that prefix ended
    total = 0
    for i, x in enumerate(a):
        total += x
        rem = total % n                              # the box of this prefix (never negative in Python)
        if rem in first_seen:                        # two in one box
            return first_seen[rem] + 1, i
        first_seen[rem] = i
    return None                                      # cannot happen: n + 1 prefixes, n boxes

### pararg
--idea
A parity argument uses odd and even to rule things out (or to prove things). Parity means whether a whole number is odd or even, and it follows simple rules: even plus even is even, odd plus odd is even, even plus odd is odd. If every allowed move changes some count in a way that keeps its parity (or flips it every time), then you know something about every reachable state without exploring any of them.
The famous example is the sliding 15 puzzle. A move swaps the blank with a neighbour. Every move changes the number of inversions (pairs of tiles in the wrong order) by an even number if the blank moves sideways, and moves the blank one row if it moves vertically. Combining these two facts gives a single parity rule that says exactly which starting boards can ever be solved. Half of all arrangements can never reach the goal.
--build
1. Pick the quantity to watch and state its parity: the number of inversions, the colour of the square, the number of moves so far, the sum modulo 2.
2. For each allowed move, work out how it changes the quantity modulo 2. Make a small table: "sideways move: changes inversions by an even amount; vertical move: changes inversions by an odd amount and changes the blank's row by one".
3. Find a combination that every move leaves unchanged. For the 15 puzzle with an odd width (like the 3 by 3 puzzle) the number of inversions stays even-or-odd as it started, and the goal has 0 inversions, so a board is solvable exactly when the inversion count is even.
4. For an even width, a vertical move changes the inversion parity and also moves the blank one row, so `inversions + (row of the blank counted from the bottom, starting at 1)` keeps its parity. The goal has the blank on row 1 and 0 inversions, giving the sum 1 (odd). A board is solvable exactly when that sum is odd (`solvable`).
5. Count inversions in code by comparing every pair of non-blank tiles, and use the piece `mod(x, 2)` to get a parity that is never negative.
6. A second example, `dominoColoursBalanced`: colour a board like a chessboard by `mod(r + c, 2)`. A domino always covers one black and one white square, so a board with a different number of each cannot be tiled. This test proves impossibility but does not prove that a balanced board can be tiled.
--think
- Signal: moves that always change something by one, swaps, flips of two items, toggling switches, tilings, "is it possible to reach", "prove that it cannot happen", "after exactly `k` moves". The words "odd" and "even", or an alternating pattern (a chessboard), are strong hints.
- Decide what to count. Candidates: parity of the total sum, parity of the number of items in a set, the colour of a cell, the permutation parity (a swap of two items flips the parity of the permutation).
- A parity argument gives a necessary condition: if it fails, the target is impossible. For sufficiency you must show a construction, or know a theorem (for the 15 puzzle the parity condition is also sufficient, which is a known result).
- Parity of a path: in a bipartite graph (a grid), every step changes the colour, so the length of a path from a cell to itself is even, and a path between cells of different colours has odd length.
- Related: invariants (parity is the simplest invariant), constructive thinking (to show reachability), XOR tricks (parity of each bit), and the modular arithmetic `mod` piece for negative numbers.
- Pitfalls: a negative number's remainder in C++ and Java is negative (use `mod`), assuming the necessary condition is sufficient, counting the blank tile as part of the inversions, and using the wrong goal layout (here the goal is `1, 2, ..., N - 1` then the blank at the bottom right).
--cost
Counting inversions by pairs is `O(N^2)` for `N` tiles (use a Fenwick tree or merge sort for `O(N log N)`). The colour check is `O(cells)`.
--java
// 15-puzzle style board: tiles in reading order, 0 is the blank, goal is 1..N-1 then 0
static boolean solvable(int[] tiles, int width) {
    int height = tiles.length / width;
    int inversions = 0, blankRowFromBottom = 1;
    for (int i = 0; i < tiles.length; i++) {
        if (tiles[i] == 0) { blankRowFromBottom = height - i / width; continue; }
        for (int j = i + 1; j < tiles.length; j++)
            if (tiles[j] != 0 && tiles[i] > tiles[j]) inversions++;    // a pair in the wrong order
    }
    if (width % 2 == 1) return mod(inversions, 2) == 0;                // piece: parity, never negative
    return mod(inversions + blankRowFromBottom, 2) == 1;
}

// necessary condition for tiling an n x m board with dominoes after removing some cells (each {r, c})
static boolean dominoColoursBalanced(int n, int m, int[][] removed) {
    int balance = 0;                              // black cells minus white cells
    for (int r = 0; r < n; r++)
        for (int c = 0; c < m; c++)
            balance += mod(r + c, 2) == 0 ? 1 : -1;
    for (int[] cell : removed)
        balance -= mod(cell[0] + cell[1], 2) == 0 ? 1 : -1;
    return balance == 0;
}

def solvable(tiles, width):
    """15-puzzle style board: tiles in reading order, 0 is the blank, goal is 1..N-1 then 0."""
    height = len(tiles) // width
    inversions, blank_row_from_bottom = 0, 1
    for i, t in enumerate(tiles):
        if t == 0:
            blank_row_from_bottom = height - i // width
            continue
        inversions += sum(1 for u in tiles[i + 1:] if u != 0 and t > u)    # pairs in the wrong order
    if width % 2 == 1:
        return inversions % 2 == 0                # mod(inversions, 2): Python's % is never negative
    return (inversions + blank_row_from_bottom) % 2 == 1

def domino_colours_balanced(n, m, removed):
    """Necessary condition for tiling an n x m board with dominoes after removing the cells in removed."""
    def colour(r, c):
        return 1 if (r + c) % 2 == 0 else -1      # mod(r + c, 2): chessboard colouring
    balance = sum(colour(r, c) for r in range(n) for c in range(m))
    return balance - sum(colour(r, c) for r, c in removed) == 0

### sqrtheur
--idea
A square root heuristic splits the work into two cases, "big" and "small", with the border at about the square root of `n`, so that each case is cheap in a different way. Neither strategy is fast on every input, but together they are, because a problem cannot be bad for both. It is like a post office with two counters: parcels under a certain size go through a quick table, big parcels get hand-checked, and there cannot be many big ones.
Example: an array with point updates and queries "sum of `a[i]` over all `i` with `i mod k = r`". If `k` is small (at most `B`, about `sqrt(n)`), keep a table `small[k][r]` that is updated on every change: an update costs `B` steps, the query one lookup. If `k` is big, there are fewer than `n / B` positions that match, so just walk them: the query costs `n / B` steps. Both are about `sqrt(n)`.
--build
1. Pick the threshold `B`. Use `B = sqrtFloor(n) + 1` (the piece `sqrtFloor(n)` gives the largest whole number whose square fits in `n`). Tune it later if the two costs differ.
2. For every small `k` from `1` to `B`, build `small[k]`, an array of `k` sums: `small[k][i mod k] += a[i]` for each `i`. This costs `n * B`.
3. Point update `a[i] = v`: let `delta = v - a[i]`, then for each small `k`, `small[k][i mod k] += delta`. Costs `B`.
4. Query with `k` small: return `small[k][r]`. Costs `1`.
5. Query with `k` big: add up `a[r], a[r + k], a[r + 2k], ...` by walking. There are at most `n / k < n / B` terms. Costs about `sqrt(n)`.
6. Total over `q` operations: `O(n sqrt n + q sqrt n)`.
7. If one case is more expensive in practice, shift `B` to balance them: the best `B` makes the two costs equal.
--think
- Signal: two natural strategies, one good when a parameter is small and one good when it is large; or a structure with "heavy" and "light" elements (a vertex with many neighbours versus few); or `n` around `10^5` where `n sqrt n` is acceptable but `n^2` is not. Also queries on `i mod k` for varying `k`.
- Decide what "small" and "large" mean and why the bad case of each strategy cannot be big at the same time. Here: a large `k` means few matching positions; a small `k` means a small table. In graph problems: a heavy vertex (degree above `sqrt(m)`) is rare (at most `2 sqrt(m)` of them), so you can handle each heavy vertex with a special method, and light vertices with a naive one.
- Related: square root decomposition (blocks of size `sqrt(n)` with a summary per block, for range queries with updates), Mo's algorithm (sort queries by block), and counting triangles in a graph by heavy and light vertices.
- If a log-factor structure (Fenwick tree, segment tree) solves it in `O(n log n)`, prefer that. Use the sqrt split when the problem has no clean structure but a threshold argument.
- Pitfalls: setting `B` badly (too big a table or too slow a walk), forgetting to update the small tables on updates, an off-by-one in the boundary (`k <= B` versus `k < B`), and memory: `B * B` cells of the table is fine, `n * B` would not be.
--cost
Preprocessing `O(n sqrt n)`, update `O(sqrt n)`, query `O(sqrt n)`. Space `O(sqrt(n)^2) = O(n)` for the table.

// ops[i] = {0, pos, value}: set a[pos] = value.  ops[i] = {1, k, r}: sum of a[j] with j mod k == r.
// returns the answers of the sum queries, in order
static List<Long> processOps(int[] input, int[][] ops) {
    int[] a = input.clone();
    int n = a.length;
    int B = (int) sqrtFloor(n) + 1;                       // piece: the border between small and big k
    long[][] small = new long[B + 1][];
    for (int k = 1; k <= B; k++) {
        small[k] = new long[k];
        for (int i = 0; i < n; i++) small[k][i % k] += a[i];
    }
    List<Long> answers = new ArrayList<>();
    for (int[] op : ops) {
        if (op[0] == 0) {                                 // update: fix every small table
            int pos = op[1];
            long delta = op[2] - a[pos];
            a[pos] = op[2];
            for (int k = 1; k <= B; k++) small[k][pos % k] += delta;
        } else if (op[1] <= B) {                          // small k: one lookup
            answers.add(small[op[1]][op[2]]);
        } else {                                          // big k: walk the few matching positions
            long s = 0;
            for (int j = op[2]; j < n; j += op[1]) s += a[j];
            answers.add(s);
        }
    }
    return answers;
}

def process_ops(inp, ops):
    """ops: (0, pos, value) sets a[pos] = value; (1, k, r) asks for the sum of a[j] with j % k == r.
    Returns the answers of the sum queries, in order."""
    a = list(inp)
    n = len(a)
    B = sqrt_floor(n) + 1                                 # piece: the border between small and big k
    small = [None] + [[0] * k for k in range(1, B + 1)]
    for k in range(1, B + 1):
        for i in range(n):
            small[k][i % k] += a[i]
    answers = []
    for kind, x, y in ops:
        if kind == 0:                                     # update: fix every small table
            delta = y - a[x]
            a[x] = y
            for k in range(1, B + 1):
                small[k][x % k] += delta
        elif x <= B:                                      # small k: one lookup
            answers.append(small[x][y])
        else:                                             # big k: walk the few matching positions
            answers.append(sum(a[y::x]))
    return answers

### localsearch
--idea
Local search starts from any answer, even a poor one, and keeps improving it with small changes until no small change helps. Picture hiking uphill in fog: you cannot see the peak, but you can always step in the direction that goes up. You stop when every neighbouring step goes down. You are then at a local optimum: the best among the nearby answers, though maybe not the best of all.
For some problems that is already a guarantee. Take the maximum cut: split the vertices of a graph into two sides to maximise the number of edges that go across. Start with any split, and as long as some vertex has more neighbours on its own side than on the other, move it to the other side. Each move adds at least one edge to the cut, and at the end every vertex has at least half of its edges crossing, so the cut holds at least half of all edges. That is within a factor of two of the best possible cut.
--build
1. Define a solution (here an array `side[v]` of 0 or 1) and a score to maximise (the number of edges whose ends are on different sides).
2. Define the neighbourhood: the small changes you allow (flip one vertex).
3. Start somewhere. A random start with the piece `randInt(0, 1)` for each vertex works, and random restarts give different local optima.
4. Loop: for each vertex `v`, count its neighbours on the same side (`same`) and on the other side (`diff`). Flipping `v` changes the cut by `same - diff`.
5. If `same > diff`, flip `v` and record that something improved. Repeat the whole sweep until nothing improves in a full pass.
6. Termination: every flip raises the score by at least 1 and the score is at most the number of edges `m`, so there are at most `m` flips.
7. Quality: at the end `diff >= same` for every vertex, so summing over all vertices, the cut has at least `m / 2` edges. Restart from several random starts and keep the best result if you want a better answer.
--think
- Signal: an optimisation problem with no exact algorithm of the needed size (NP-hard problems, huge search spaces), where any answer is easy to get and a small change is easy to score. Also timetabling, travelling salesman tours (2-opt swaps), clustering, and puzzles with a "number of violated rules" score.
- Decide the neighbourhood: bigger neighbourhoods find better optima but cost more per step. Decide the acceptance rule: strict improvement (hill climbing), or sometimes accepting worse moves (simulated annealing) to escape local optima.
- To escape: random restarts (run many times, keep the best), accepting a worse move with a small probability that shrinks over time (annealing), or a tabu list that forbids undoing recent moves.
- Local search gives no guarantee unless you prove one, as for max cut above. If you need a guarantee, use an approximation algorithm; if you need the exact optimum, use search with pruning or dynamic programming.
- Related: randomization (starts and tie-breaks), greedy (a one-pass special case), approximation algorithms.
- Pitfalls: cycling forever when the move does not strictly improve the score (use strict improvement or a step limit), keeping no copy of the best-so-far across restarts, and slow scoring (update the score incrementally with the `same - diff` trick, not from scratch).
--cost
Each pass is `O(n + m)`. There are at most `m` improving flips, so `O(m (n + m))` in the worst case, and much less in practice.
--java
// a split of the vertices into sides 0 and 1; at least half of the edges cross it
static int[] localMaxCut(int n, int[][] edges) {
    List<List<Integer>> adj = new ArrayList<>();
    for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
    for (int[] e : edges) { adj.get(e[0]).add(e[1]); adj.get(e[1]).add(e[0]); }
    int[] side = new int[n];
    for (int v = 0; v < n; v++) side[v] = randInt(0, 1);      // piece: a random start
    boolean improved = true;
    while (improved) {
        improved = false;
        for (int v = 0; v < n; v++) {
            int same = 0, diff = 0;
            for (int w : adj.get(v)) { if (side[w] == side[v]) same++; else diff++; }
            if (same > diff) { side[v] ^= 1; improved = true; }   // flipping gains same - diff > 0
        }
    }
    return side;
}

// number of edges that go between the two sides
static int cutSize(int[] side, int[][] edges) {
    int cut = 0;
    for (int[] e : edges) if (side[e[0]] != side[e[1]]) cut++;
    return cut;
}

def local_max_cut(n, edges):
    """A split of the vertices into sides 0 and 1; at least half of the edges cross it."""
    adj = [[] for _ in range(n)]
    for a, b in edges:
        adj[a].append(b)
        adj[b].append(a)
    side = [rand_int(0, 1) for _ in range(n)]                 # piece: a random start
    improved = True
    while improved:
        improved = False
        for v in range(n):
            same = sum(1 for w in adj[v] if side[w] == side[v])
            diff = len(adj[v]) - same
            if same > diff:
                side[v] ^= 1                                  # flipping gains same - diff > 0
                improved = True
    return side

def cut_size(side, edges):
    """Number of edges that go between the two sides."""
    return sum(1 for a, b in edges if side[a] != side[b])

### approx
--idea
An approximation algorithm gives an answer that is not always optimal but is guaranteed to be close: within a known factor of the best possible. It is used when finding the exact best answer is too slow (the problem is NP-hard, which means no fast method is known and probably none exists). Instead of giving up, you accept an answer at most, say, twice as bad as the best, and you can prove that, even though you never find out what the best is.
The example is the vertex cover: choose the fewest vertices so that every edge has at least one end chosen. Exact is hard. The approximation: scan the edges; whenever you meet an edge with neither end chosen, choose both ends. The edges you pick this way share no vertex (a matching), and any cover must include at least one end of each of them, so the best cover has at least as many vertices as your matching has edges. You chose two per matching edge, so you are within a factor of 2.
--build
1. State the problem and what "better" means (fewest vertices that touch every edge).
2. Find a simple, fast rule that always gives a valid answer. Here: scan the edges in any order and, for an edge `(u, v)` with both ends still unchosen, choose both.
3. Argue the answer is valid. After the scan every edge has a chosen end: either one end was chosen earlier, or both are chosen now.
4. Find a lower bound on the best answer. The edges that triggered a choice form a matching (no two share a vertex, since the first end would already be chosen). Any cover needs a different vertex for each of these edges, so `OPT >= matching size`.
5. Compare: you chose `2 * matching size` vertices, so `answer <= 2 * OPT`. This is a 2-approximation.
6. Implement (`vertexCover`): a boolean array `chosen`, one pass over the edges.
7. Test: on small graphs compute the optimum by brute force and confirm `answer <= 2 * OPT` and that the answer is a valid cover.
--think
- Signal: a hard optimisation problem (vertex cover, set cover, travelling salesman, bin packing, knapsack variants) with large input where exact search is impossible, and the statement allows a slightly worse answer ("within a factor of 2", "at least half as good", or a scoring formula).
- Decide the guarantee you need. A factor like 2 is fine for many tasks; a better factor needs more complex methods. For some problems no good approximation exists unless a famous conjecture fails (so do not search for one).
- The recipe for the proof: (1) show the algorithm's answer is valid, (2) find a lower bound for the optimum (a matching, a relaxed version, a simple count), (3) compare your cost to that bound. Without a lower bound you cannot prove a ratio.
- Famous examples: vertex cover by maximal matching (factor 2), greedy set cover (factor `ln n`), metric travelling salesman by a minimum spanning tree (factor 2), list scheduling for makespan (factor 2), and first-fit decreasing for bin packing.
- If it is only a heuristic with no proof, say so; local search and randomisation often give better answers in practice than provable methods, but with no promise.
- Pitfalls: confusing "valid" with "good" (always check validity first), a bound that is not actually a lower bound for the optimum, and assuming a greedy rule that looks natural has a guarantee (greedy by highest degree for vertex cover has none better than `log n`).
--cost
`O(n + m)` for the matching-based cover. Space `O(n)`.
--java
// a vertex cover with at most twice as many vertices as the smallest possible one
static List<Integer> vertexCover(int n, int[][] edges) {
    boolean[] chosen = new boolean[n];
    List<Integer> cover = new ArrayList<>();
    for (int[] e : edges) {
        if (!chosen[e[0]] && !chosen[e[1]]) {      // an edge no chosen vertex touches
            chosen[e[0]] = chosen[e[1]] = true;    // take both ends: this edge joins a matching
            cover.add(e[0]);
            cover.add(e[1]);
        }
    }
    return cover;
}

### online
--idea
An online algorithm must make each decision as the input arrives, without knowing what comes next, and cannot take a decision back. You compare it with an offline algorithm that sees the whole future. The measure is the competitive ratio: the worst case of (your cost) divided by (the best cost with full knowledge). A ratio of 2 means you never pay more than twice what a fortune teller would.
The classic is ski rental. Skis cost `B` to buy or 1 per day to rent, and you do not know how many days you will ski. If you buy at once and then stop after one day, you wasted `B`. If you rent forever, you may pay far more than `B`. The balanced rule: rent for `B - 1` days, and if you are still skiing on day `B`, buy. You never pay more than `2B - 1` while the best choice in hindsight pays `min(days, B)`, so the ratio is below 2.
--build
1. Write down the decisions in order and what is known at each moment (only the past).
2. Write the offline optimum, assuming the whole future is known. Ski rental: `min(days, B)`.
3. Pick a rule that uses only the past. Ski rental: rent until the money spent on renting equals the price of buying, then buy (`skiRentalOnline`).
4. Prove the ratio against every possible future. For ski rental: if the season is shorter than `B` days you pay the same as the optimum; if it is at least `B` days you pay `(B - 1) + B = 2B - 1` while the optimum pays `B`.
5. Second example, caching: a cache holds `k` pages. When a page is not in it (a fault) you must bring it in and, if the cache is full, evict one. The offline best evicts the page used farthest in the future (`beladyFaults`). The online rule LRU (least recently used) evicts the page unused the longest (`lruFaults`).
6. LRU is `k`-competitive: it never faults more than `k` times as often as the optimum (plus at most `k` extra faults at the start). No online rule does better in the worst case.
7. In code, keep the cache as an ordered list of pages where the front is least recently used: on a hit move the page to the back, on a fault evict the front if full, then add the page at the back.
--think
- Signal: decisions in real time with no knowledge of the future: caching, renting or buying, scheduling jobs as they arrive, ad allocation, routing requests. Phrases like "online", "as they arrive", "without knowing the future", "competitive".
- Decide the adversary: the worst future. The competitive ratio is decided by the worst input, so look for the sequence that makes your rule look foolish (for ski rental, "stop skiing the day after you buy").
- To prove a ratio: compare your cost with the offline optimum on every input, usually by splitting the input into phases and counting costs per phase. To prove a rule is the best possible, build an input that forces any rule to pay at least that ratio.
- Practical view: LRU and its variants work much better than the worst case suggests, because real request sequences have locality (recently used pages are used again).
- Related: greedy (a decision with no regret), amortised analysis (cost over a sequence), randomisation (random online rules can beat the best deterministic ratio, for example randomised ski rental gets about `e / (e - 1)`).
- Pitfalls: confusing "online" (no future knowledge) with "streaming" (little memory), comparing with the wrong baseline (it is the offline optimum on the same input), and forgetting the additive constant in a ratio.
--cost
Ski rental decision `O(days)` in the simulation. LRU with a linked hash structure `O(1)` per request (the list version below is `O(k)` per request). Belady `O(n k)` for `n` requests.
--java
// cost of "rent until the rent paid equals the price, then buy"
static long skiRentalOnline(long buyCost, long days) {
    long cost = 0;
    for (long day = 1; day <= days; day++) {
        if (day == buyCost) { cost += buyCost; break; }   // still skiing on day B: buy
        cost += 1;                                        // otherwise rent
    }
    return cost;
}

// best possible cost if the number of days were known in advance
static long skiRentalOptimal(long buyCost, long days) {
    return Math.min(days, buyCost);
}

// page faults of LRU with a cache of k pages
static int lruFaults(int k, int[] requests) {
    LinkedList<Integer> cache = new LinkedList<>();        // front = least recently used
    int faults = 0;
    for (int page : requests) {
        if (cache.remove((Integer) page)) {                // hit: it moves to the back
            cache.addLast(page);
            continue;
        }
        faults++;
        if (cache.size() == k) cache.removeFirst();        // full: evict the least recently used
        cache.addLast(page);
    }
    return faults;
}

// page faults of the offline best rule: evict the page whose next request is farthest away
static int beladyFaults(int k, int[] requests) {
    List<Integer> cache = new ArrayList<>();
    int faults = 0;
    for (int i = 0; i < requests.length; i++) {
        if (cache.contains(requests[i])) continue;
        faults++;
        if (cache.size() == k) {
            int victim = 0, farthest = -1;
            for (int j = 0; j < cache.size(); j++) {
                int next = requests.length;                // never used again
                for (int t = i + 1; t < requests.length; t++)
                    if (requests[t] == cache.get(j)) { next = t; break; }
                if (next > farthest) { farthest = next; victim = j; }
            }
            cache.remove(victim);
        }
        cache.add(requests[i]);
    }
    return faults;
}

    """Best possible cost if the number of days were known in advance."""
    return min(days, buy_cost)

def lru_faults(k, requests):
    """Page faults of LRU with a cache of k pages."""
    cache, faults = [], 0                            # front = least recently used
    for page in requests:
        if page in cache:                            # hit: it moves to the back
            cache.remove(page)
            cache.append(page)
            continue
        faults += 1
        if len(cache) == k:
            cache.pop(0)                             # full: evict the least recently used
        cache.append(page)
    return faults

def belady_faults(k, requests):
    """Page faults of the offline best rule: evict the page whose next request is farthest away."""
    cache, faults = [], 0
    for i, page in enumerate(requests):
        if page in cache:
            continue
        faults += 1
        if len(cache) == k:
            def next_use(p):
                rest = requests[i + 1:]
                return rest.index(p) if p in rest else len(requests)   # never used again
            cache.remove(max(cache, key=next_use))
        cache.append(page)
    return faults

// page faults of LRU with a cache of k pages
int lruFaults(int k, const vector<int>& requests) {
    deque<int> cache;                                     // front = least recently used
    int faults = 0;
    for (int page : requests) {
        auto it = find(cache.begin(), cache.end(), page);
        if (it != cache.end()) {                          // hit: it moves to the back
            cache.erase(it);
            cache.push_back(page);
            continue;
        }
        faults++;
        if ((int)cache.size() == k) cache.pop_front();    // full: evict the least recently used
        cache.push_back(page);
    }
    return faults;
}

// page faults of the offline best rule: evict the page whose next request is farthest away
int beladyFaults(int k, const vector<int>& requests) {
    vector<int> cache;
    int faults = 0, n = requests.size();
    for (int i = 0; i < n; i++) {
        if (find(cache.begin(), cache.end(), requests[i]) != cache.end()) continue;
        faults++;
        if ((int)cache.size() == k) {
            int victim = 0, farthest = -1;
            for (int j = 0; j < (int)cache.size(); j++) {
                int next = n;                             // never used again
                for (int t = i + 1; t < n; t++)
                    if (requests[t] == cache[j]) { next = t; break; }
                if (next > farthest) { farthest = next; victim = j; }
            }
            cache.erase(cache.begin() + victim);
        }
        cache.push_back(requests[i]);
    }
    return faults;
}
